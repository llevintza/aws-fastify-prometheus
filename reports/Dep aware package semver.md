# Classify dependency bumps by consumer contract

`@llevintza/fastify-prometheus-metrics` should version a dependency update by what its own consumers can observe, and should treat the dependency's patch, minor, or major digit as a hint that still has to pass that test. SemVer calls a dependency change that leaves the public API alone a compatible release: patch when the point is a fix or a private adaptation, minor when this package adds behavior, and major only when the public contract breaks ([SemVer 2.0.0](https://semver.org/)). For this 1.0.2 plugin that contract is the Fastify peer `^4.0.0 || ^5.0.0`, the `fp()` range `4.x || 5.x`, `engines.node` of `>=22.0.0`, the exported plugin and `typeof register` option, and the scrape text returned by `getMetrics()` and the metrics route ([package.json](file:///Users/llevintza/orca/workspaces/aws-fastify-prometheus/dependabot-stacked-prs/package.json), [plugin sources](file:///Users/llevintza/orca/workspaces/aws-fastify-prometheus/dependabot-stacked-prs/src/plugin.ts)). The encoding that still works after `gh pr merge --merge`, a manual merge, and a stack that lands in one push is **one `analyzeCommits` plugin** that reads each Dependabot commit's `updated-dependencies` YAML and that commit's `package.json` diff. Dependabot's commit prefix cannot vary by update type, and a body glob cannot see `version-update:semver-*` inside a real commit message ([Dependabot commit-message](https://docs.github.com/en/code-security/dependabot/dependabot-version-updates/configuration-options-for-the-dependabot.yml-file#commit-message), [micromatch](https://github.com/micromatch/micromatch)). The current retitle-and-`--subject` plan, which turns every `version-update:semver-major` into `feat(deps)`, has to become a human raise used only when the plugin deliberately publishes nothing. Left as the automatic map, that **`feat` subject outranks a correct patch** and ships a minor for an encapsulated major.

## SemVer keeps a dependency major in the compatible band

The spec never builds a ladder from the dependency's digit to the library's digit. After 1.0.0, **major means a backward-incompatible change to the public API** this package declares, minor means compatible public API (and is the optional level for a substantial private improvement), and patch means a compatible fix ([SemVer 2.0.0](https://semver.org/)). The dependency FAQ is direct: updating one's own dependencies without changing the public API "would be considered compatible," and the choice between patch and minor "depends on whether you updated your dependencies in order to fix a bug or introduce new functionality," with new functionality expected to come with additional code ([SemVer FAQ](https://semver.org/#what-should-i-do-if-i-update-my-own-dependencies-without-changing-the-public-api)). npm's bump table is the same generic one, plus a recommendation to increment major "if you introduce a change that breaks a package dependency," which means consumers can no longer take the upgrade under the compatibility promise ([npm semantic versioning](https://docs.npmjs.com/about-semantic-versioning/)). Neither document contains a row that says a dependency major is a package minor.

Maintainer practice splits the three dependency kinds the naive ladder collapses. A devDependency bump usually does not change the published version. A runtime dependency bump is usually a patch unless the library wraps that dependency's API and the wrapped API changed, or the library elects the spec's optional private-improvement minor. A peer range that grows while every previously accepted host still installs is a minor; a peer range that drops a previously valid host is a major ([8 Hobbies](https://8hob.io/posts/semantic-versioning-npm-packages-after-dependency-update/), [semver#502](https://github.com/semver/semver/issues/502)). On the SemVer tracker the clearest case split is the same: a fully internalized dependency major, worked around with no public API change, is a library patch; the same major plus new public API is a library minor; re-exported types that broke, or public features that had to be removed, is a library major ([semver#148](https://github.com/semver/semver/issues/148)). A later comment in that thread warns that a spurious library major strands the previous line on the old dependency, because fixes then land only on the new major. That is the practical cost of mapping every dependency major to a package minor or major by reflex.

Two further gates decide whether a release exists at all. **`package-lock.json` is not published**, so an in-range lockfile refresh does not change what downstream installers resolve; a release of this library would not deliver the bump ([Node.js dependency guidelines](https://github.com/nodejs/package-maintenance/blob/main/docs/dependency-management-guidelines.md)). A change to a published range does require a new version, because a released manifest must not be modified in place ([SemVer 2.0.0](https://semver.org/)). Dropping Node versions is a breaking change of this package, including when a dependency upgrade is what forces the drop ([Node.js dependency guidelines](https://github.com/nodejs/package-maintenance/blob/main/docs/dependency-management-guidelines.md)). semantic-release's own maintainers encode a production dependency update as `fix`, which is a patch even when the dependency moved a major, and they treat a GitHub Actions bump as something consumers should not see ([semantic-release#1329](https://github.com/semantic-release/semantic-release/issues/1329), [commit-analyzer#536](https://github.com/semantic-release/commit-analyzer/issues/536)). The naive middle rung, dependency major to package minor, is the step that does not appear in the spec, in npm's table, or in that tooling default.

## prom-client, Fastify, and the AWS SDK do not share a digit

This package has three production dependencies and one peer, and each one fails the shared ladder in a different direction. `prom-client` follows SemVer and has already broken wrappers on purpose. v13.0.0 made `registry.metrics()` and the related getters async. v14.0.0 changed `linearBuckets` so histogram bucket labels can change. v15.0.0 dropped a set of Node majors and added OpenMetrics and exemplars. On 2026-08-24 the Prometheus project renamed the module to `@prometheus-io/client` at 0.16.0, with breaks that include counter exemplars reporting the value instead of the delta, `MetricType` becoming a string union, and Node 16, 18, 20, 21, and 23 dropped; unreleased notes say gauges will no longer initialize to zero ([prom-client changelog](https://github.com/prometheus/client_js/blob/main/CHANGELOG.md), [v13.0.0](https://github.com/siimon/prom-client/releases/tag/v13.0.0), [v15.0.0](https://github.com/siimon/prom-client/releases/tag/v15.0.0)). This plugin's route and `getMetrics(): Promise<string>` both return `metricsRegistry.metrics()`, and the public options type the registry as `typeof register` from `prom-client` ([plugin sources](file:///Users/llevintza/orca/workspaces/aws-fastify-prometheus/dependabot-stacked-prs/src/plugin.ts)). A prom-client major that changes that string, those types, or exemplar and gauge defaults is a package major because callers observe it. A prom-client major whose only break is a Node floor this package's `>=22` already exceeds, with identical types and identical scrape text, is a patch. The 0.16.0 notes do not state the new Node minimum, so "Node 22 is still supported" cannot be read off that list. Switching the dependency to `@prometheus-io/client` is a package major for a separate reason: the public option accepts a `prom-client` registry, and the module identity moved.

`fastify` is the peer, so its digit is an install contract. Official Fastify plugins publish one plugin major per Fastify major and leave the old line in place (`@fastify/sensible` 6/5/4 for Fastify 5/4/3) ([@fastify/sensible](https://github.com/fastify/fastify-sensible), [fastify-plugin](https://github.com/fastify/fastify-plugin/)). This package's single version advertising `^4 || ^5` is the widen pattern: valid while the code and the `fp()` metadata truly accept both, and a later **deletion of `^4` is a package major** even though Fastify 4 left LTS on **2025-06-30** ([Fastify LTS](https://fastify.dev/docs/latest/Reference/LTS/)). Adding a future `|| ^6` while `^4` and `^5` remain is **the one dependency-major event that is a package minor**, and it is a range widen. A pull request that only moves the `fastify` devDependency and leaves both the peer and the `fp()` string alone publishes nothing. Fastify sometimes ships breaking security fixes as a minor and documents them; a plugin does not cut a major for each host minor ([Fastify LTS](https://fastify.dev/docs/latest/Reference/LTS/)).

`fastify-plugin` is a runtime helper, not the host. Consumers do not select it the way they select Fastify. v6.0.0 (2026-06-09) is devDependency and structure work plus a removed deprecated interface; v6.0.1 throws on a nullish plugin and stops mutating options ([v6.0.0](https://github.com/fastify/fastify-plugin/releases/tag/v6.0.0), [v6.0.1](https://github.com/fastify/fastify-plugin/releases/tag/v6.0.1)). Its README ties helper majors to Fastify majors only through v4, and a third-party reading says v6 declares no `peerDependencies` and that the range passed to `fp()` is what Fastify checks ([fastify-plugin](https://github.com/fastify/fastify-plugin/), [opena2a commit](https://github.com/opena2a-org/agent-identity-management/commit/b20a51bfbf17acb89595400c157d5da0a82af47b)). Until a type diff of this package's default export says otherwise, a `fastify-plugin` major is a package patch when `fp(plugin, { fastify, name })` still typechecks and the peer string is unchanged. The group name `fastify-ecosystem-major` is not that test.

`@aws-sdk/client-cloudwatch` is the case that makes the digit actively misleading. The JS SDK v3 "usually" releases once per weekday and increments the minor component each time, and Node floors have moved inside 3.x, including `>=20` at 3.968.0 ([aws-sdk-js-v3 README](https://github.com/aws/aws-sdk-js-v3/blob/main/README.md)). An AWS maintainer stated that the SDK is **"not releasing changes in adherence to semver,"** because the product generation occupies the major component ([aws-sdk-js-v3#5818](https://github.com/aws/aws-sdk-js-v3/issues/5818)). The cross-SDK policy separately reserves the right to drop an underlying dependency without a major ([AWS maintenance policy](https://docs.aws.amazon.com/sdkref/latest/guide/maint-policy.html)). This exporter does not construct `CloudWatchClient`; its config type is the plugin's `AwsExporterConfig` ([aws-metrics-exporter.ts](file:///Users/llevintza/orca/workspaces/aws-fastify-prometheus/dependabot-stacked-prs/src/aws-metrics-exporter.ts)). While that stays true, an SDK bump of any level is a **package patch if `engines` stays `>=22`**, and it is a package major only when the floor moves above 22 or callers have to change `AwsExporterConfig` or `exportMetric`. Publishing the wrapper on every weekday SDK release is the failure mode a New Relic maintainer already called untenable ([aws-sdk-js-v3#4153](https://github.com/aws/aws-sdk-js-v3/issues/4153)). In-range lockfile movement publishes nothing. A raised floor in `package.json` publishes a patch, because the manifest consumers install has changed and the contract has not.

Security severity does not add a rank. A fix that leaves exports, the peer range, engines, and scrape text compatible is a **patch, including when the fixed dependency version is a major**, so existing `^1.x` installs can take it ([SemVer 2.0.0](https://semver.org/), [npm semantic versioning](https://docs.npmjs.com/about-semantic-versioning/)). The repo's `security-critical` group selects production majors and then excludes `fastify*`, `@fastify/*`, `@aws-sdk/*`, and `prom-client`, which is every current production dependency, and no group sets `applies-to` ([dependabot.yml](file:///Users/llevintza/orca/workspaces/aws-fastify-prometheus/dependabot-stacked-prs/.github/dependabot.yml)). It is not a CVSS bucket. GitHub still opens a separate security pull request when a version-update group already touches the vulnerable package ([dependabot-core discussion #10645](https://github.com/dependabot/dependabot-core/discussions/10645)). Classify that pull request on its own.

## Ten rows, then a max, then a hold for the unreadable break

Apply the first matching row to each dependency. "Contract" means exported types and values, `fastify.prometheus`, the peer range, the `fp()` `fastify` string, `engines.node`, and Prometheus scrape text. Rank order for the rollup is `none < patch < minor < major`.

| # | If this is true | Package release |
| --- | --- | --- |
| 1 | GitHub Actions, or a devDependency that is not also the `fastify` peer, and `dist`, `engines`, and the peer range are unchanged | `none` |
| 2 | The commit touches only the lockfile; `dependencies`, `peerDependencies`, and `engines` are unchanged | `none` |
| 3 | The peer range or the `fp()` `fastify` string drops a major or raises a floor so a previously valid host no longer installs, or `engines.node` moves up | `major` |
| 4 | The peer range adds a major and still accepts every previously valid host | `minor` |
| 5 | The dependency is `prom-client` at `semver-major`, or the package name switches to `@prometheus-io/client` | hold: publish nothing until a human subject |
| 6 | `prom-client` is patch or minor and the changelog does not show a scrape or `register` break | `patch` |
| 7 | `fastify-plugin` at any level, `fp(plugin, { fastify, name })` still typechecks, peer and engines unchanged | `patch` |
| 8 | `@aws-sdk/*` at any level, client still not imported, `AwsExporterConfig` unchanged, `engines` unchanged | `patch` |
| 9 | A production dependency adds caller-visible behavior and the contract still holds | `minor` |
| 10 | A production dependency of any level, including a security fix, with no contract change | `patch` |

Rows 6 and 9 are the human-readable leftovers of the spec, not something the YAML trailer can prove. A prom-client minor that changes default scrape text is a package major if existing scrapes break and a package minor if the addition is purely additive; the trailer only says `semver-minor`. The plugin should ship row 6 as patch, and a human who has read the changelog raises that one pull request with a breaking subject. Row 5 stays unpublished by automation because the expensive mistake is a `2.0.0` that strands `^1.x`, and the analyzer cannot take that major back once it has emitted it. OpenJS guidance asks a human to choose the version at publish time ([OpenJS secure releases](https://github.com/openjs-foundation/security-wg/blob/main/docs/Secure_Releases/secure-releases.md)). This repo already publishes with semantic-release, so the honest split is to automate the rows a diff can decide and to hold the row whose answer lives in an upstream changelog.

The pull request's release is the **max of those per-dependency ranks**. A member scored `none` does not pull the max down, and a member whose own version is major does not raise the max unless its row says so. An `aws-ecosystem` pull request full of SDK majors is still a package patch while the client stays unimported. A `fastify-ecosystem-major` pull request is a package major only when row 3 matches, a patch when it is `fastify-plugin` under row 7, and nothing when it is only the Fastify dev install. Group identifiers are review labels. `monitoring-tools` is already minor and patch for `prom-client`, so a prom-client major arrives alone and can be held ([dependabot.yml](file:///Users/llevintza/orca/workspaces/aws-fastify-prometheus/dependabot-stacked-prs/.github/dependabot.yml)). Dependabot will not compute this rollup. `dependabot/fetch-metadata`'s scalar `update-type` is defined as **the highest semver change in the pull request**, so one SDK major inside a mixed group forces `version-update:semver-major` even when every member is a package patch ([fetch-metadata](https://github.com/dependabot/fetch-metadata/)). The classifier has to walk `updated-dependencies-json`, or the per-item YAML, and ignore `direct:development`.

When the max is `major` and another member is a security fix that would have been `patch`, split the fix onto its own pull request before merge. A grouped pull request is all-or-nothing, and one breaking member holds every other fix ([Apache Dependabot guidance](https://infra.apache.org/dependabot.html)). semantic-release then keeps a single level for the whole tag range, the highest one, so a patch commit and a major commit that land in the same push become one major and the patch never exists on `1.x` ([commit-analyzer](https://github.com/semantic-release/commit-analyzer/blob/master/index.js)). eslint, Jest, typescript, semantic-release, husky, prettier, commitlint, and GitHub Actions follow row 1. A TypeScript bump that changes emitted `.d.ts` or runtime JavaScript in `dist` is classified as a code change. A TypeScript bump that fails CI until config is adjusted, and then emits the same `dist`, stays `none`. Shipping a package patch for an eslint major would train consumers to ignore version numbers.

## Prefixes, titles, and body globs drop the severity on the floor

Dependabot can put `chore(deps)` or `chore(deps-dev)` in the subject and nothing else. `commit-message` offers `prefix`, `prefix-development`, and `include: scope`. Groups have no commit-message field, and nothing keys the prefix off major, minor, or patch ([Dependabot options](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)). This repo already sets those two prefixes and `include: scope`. A second `updates` block for the same manifest still has one prefix. The documented workaround of `prefix: fix` publishes every production bump, including dependency majors and SDK weekday floors, as a package patch ([mattbun](https://mattbun.io/posts/semantic-release-dependabot/)). That is the naive ladder's first rung frozen into git, and it fights a later plugin that wanted a different level, because semantic-release keeps the higher of the two.

The severity that does exist is already in the commit body. Dependabot writes one commit per version-update pull request and a YAML trailer of `dependency-name`, `dependency-type`, and `update-type: version-update:semver-patch|semver-minor|semver-major`, repeated once per member of a group ([fetch-metadata#632](https://github.com/dependabot/fetch-metadata/pull/632), [dependabot-core#8217](https://github.com/dependabot/dependabot-core/issues/8217)). Grouped subjects say "bump the GROUP group" and do not carry versions; "Updates `name` from A to B" lines are the second source for both versions. `dependency-version` has been missing on grouped commits and present on later ones. One commit per dependency inside a group was still an open request in 2024 ([dependabot-core#8450](https://github.com/dependabot/dependabot-core/issues/8450)). There is no trailer bit for "breaking for consumers of this package."

`releaseRules` cannot read that trailer. String criteria are micromatch globs. On micromatch 4.0.8, `*` matches a slash-free toy line and **does not match across `/`**, so `*semver-major*`, `**semver-major**`, and `**` all fail on a realistic Dependabot body that contains release-note URLs. `String` inclusion of `version-update:semver-major` succeeds on that same body ([micromatch](https://github.com/micromatch/micromatch)). A `release` value cannot be a function; a rule module must export an array, and a function export throws ([load-release-rules.js](https://github.com/semantic-release/commit-analyzer/blob/master/lib/load-release-rules.js)). `parserOpts.noteKeywords` only marks a commit breaking, which is package major ([commit-analyzer](https://github.com/semantic-release/commit-analyzer?tab=readme-ov-file)). No maintained semantic-release plugin was found that maps Dependabot `update-type` onto patch versus minor versus major. `@amanda-mitchell/semantic-release-notify-dependabot` notifies Dependabot after a private publish and does not analyze commits ([npm](https://www.npmjs.com/package/@amanda-mitchell/semantic-release-notify-dependabot)).

What semantic-release 25 actually scores is `git log <lastTag>..<head>` with the full message, merge commits included, because `getCommits` does not pass `--no-merges` ([lib/git.js](https://github.com/semantic-release/semantic-release/blob/master/lib/git.js)). **`gh pr merge --merge` keeps the Dependabot commit** and adds one merge commit. The default subject `Merge pull request #N from ...` does not match the conventionalcommits header, so that commit releases nothing ([conventionalcommits parser](https://github.com/conventional-changelog/conventional-changelog/blob/master/packages/conventional-changelog-conventionalcommits/src/parser.js), [troubleshooting](https://github.com/semantic-release/semantic-release/blob/master/docs/support/troubleshooting.md)). Today's auto-merge runs `gh pr merge --merge --auto --body "🤖 Auto-merged safe patch update"` and does not pass `--subject`, so the headline stays the default and the Dependabot commit stays `chore` ([dependabot-auto-merge.yml](file:///Users/llevintza/orca/workspaces/aws-fastify-prometheus/dependabot-stacked-prs/.github/workflows/dependabot-auto-merge.yml)). Under the current `.releaserc.js`, **`{ type: 'chore', release: false }` matches `chore(deps)` and `chore(deps-dev)`** for patch, minor, and major bumps, and it also matches `chore(deps)!` and a `BREAKING CHANGE:` footer on a chore, because every breaking rule in the file also requires `feat`, `fix`, `perf`, or `refactor`. `fix!:` and `feat!:` return major. Measured on `@semantic-release/commit-analyzer` 13.0.1 ([analyze-commit.js](https://github.com/semantic-release/commit-analyzer/blob/master/lib/analyze-commit.js)).

A custom `analyzeCommits` is the mechanism that can see the raw `%B` text. If several plugins implement that step, semantic-release keeps the highest of `patch`, `minor`, and `major`; a falsy result does not outrank a real level, and a second plugin can raise a commit the stock analyzer ignored and **cannot lower a major** the stock analyzer already returned ([plugins.js](https://github.com/semantic-release/semantic-release/blob/master/lib/definitions/plugins.js)). Labels, the Dependabot API, and `fetch-metadata` outputs are not on the commit. `fetch-metadata` is reliable on a bot-only pull request and goes blank once any non-Dependabot commit is pushed, unless verification is skipped ([fetch-metadata](https://github.com/dependabot/fetch-metadata/)). Calling it from the release job re-derives text that is already in git and makes the publish depend on a token. The release workflow already checks out `main` with `fetch-depth: 0` ([ci.yml](file:///Users/llevintza/orca/workspaces/aws-fastify-prometheus/dependabot-stacked-prs/.github/workflows/ci.yml)), so the plugin can `git show <hash> -- package.json` and apply rows 2, 3, 4, and 8 from the diff.

The plugin should be the **only `analyzeCommits` implementation**, wrapping the existing conventional rules plus the trailer table, and it should return one level for the range:

Walk each commit. Drop any message semantic-release would already drop for `[skip release]` or `[release skip]`. `[skip ci]` does not do that ([plugins.js](https://github.com/semantic-release/semantic-release/blob/master/lib/definitions/plugins.js)). Score a conventional `feat`, `fix`, `perf`, or `refactor` with the rules this repo already has, including type-qualified breaking notes, which is how `feat(deps)!:` plus a one-line `BREAKING CHANGE:` becomes a package major. For a commit whose body contains `updated-dependencies`, parse every item. Ignore `direct:development`. If that commit's `package.json` diff does not change `dependencies`, `peerDependencies`, or `engines`, score the commit `none` even when the trailer is present. Otherwise score each production item with the table, using `dependency-name` and `update-type`, and take the max inside the commit. Row 5 scores `none`. Take the max across commits. A default merge subject adds nothing, so a manual merge of a confident row still publishes, and a manual merge of a held prom-client major publishes nothing until somebody supplies `fix(deps):`, `feat(deps):`, or `feat(deps)!:`.

A `Release-As` trailer looks like a clean override and does not survive this history model. commit-analyzer never reads `release-as`; the notes writer only un-hides a commit whose body matches that pattern ([writer.js](https://github.com/conventional-changelog/conventional-changelog/blob/master/packages/conventional-changelog-conventionalcommits/src/writer.js)). The commit context used here carries hash, full message, tags, and committer date, and this research did not confirm parent SHAs, so a trailer on the merge commit cannot be tied to one parent Dependabot commit. A stack that lands together is one analysis range ([Merging stacked pull requests](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-stacked-pull-requests)). A range-wide `Release-As: patch` would also suppress a real `feat` that landed in the same push, or mis-label every layer. Confident rows are policy: the way to avoid the patch is to not merge. Uncertain rows publish nothing until a conventional subject raises them. That subject is a separate commit, the max works, and no parent linkage is required.

Rewriting the Dependabot commit is the approach to reject. Dependabot's rebase is not `git rebase`; it reruns the update and drops the previous history ([dependabot-core#2882](https://github.com/dependabot/dependabot-core/issues/2882)). Extra commits on `dependabot/*` stop that rebase unless the message contains one of the `[dependabot skip]` tokens, and they blank `fetch-metadata` ([Managing Dependabot pull requests](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/manage-your-dependency-security/manage-dependabot-prs)). The next scheduled run rebuilds the bot commit anyway. `GH_TOKEN` on the existing `pull_request_target` workflow can retitle and merge. It should not push rewritten commits.

Two failure modes are already measured and have to stay closed. A catch-all `{ type: 'chore', release: false }` placed after `{ type: 'chore', scope: 'deps', release: 'patch' }` swallows the patch, because `release: false` is not in the rank list, `indexOf(false)` is `-1`, and that value compares as higher than `patch` while a `false` match does not stop the loop. With `false` first and the scope rule after it, `chore(deps)` is a patch and `chore(deps-dev)` stays quiet. A `major` match does stop the loop, so a later `false` cannot clear it ([compare-release-types.js](https://github.com/semantic-release/commit-analyzer/blob/master/lib/compare-release-types.js), [udibo/juniper#78](https://github.com/udibo/juniper/pull/78)). The plugin path avoids that order bug by not adding a coarse `chore(deps)` rule at all. The other trap is the release commit. `@semantic-release/git` commits `chore(release): ${version} [skip ci]` plus the generated notes. A notes body that still contains `BREAKING CHANGE:` parses as a breaking note. Under today's type-qualified rules the result stays `false`. An unqualified `{ breaking: true, release: 'major' }` turns the next release commit into another major, and `[skip ci]` does not stop the second analysis ([plugins.js](https://github.com/semantic-release/semantic-release/blob/master/lib/definitions/plugins.js)). Keep the breaking rules type-qualified. The plugin must score breaking notes the way the parser does, on `feat` / `fix` / `perf` / `refactor`, and must not treat the string `BREAKING CHANGE` inside a `chore(release)` body as a new major. Passing the Dependabot pull-request body through `--body`, or setting the repository merge message to the pull-request description, can paste upstream changelog lines that start with `BREAKING CHANGE` onto a `feat` or `fix` merge commit and promote it the same way.

`conventional-changelog-conventionalcommits` 10.4.1 **hides `chore` with `effect: 'hidden'`**. Hiding is independent of whether the analyzer releases. A type entry with no `effect` is shown, `findTypeEntry` returns the first matching type whose scope is unset or equal, and passing `presetConfig.types` replaces the whole default list ([constants.js](https://github.com/conventional-changelog/conventional-changelog/blob/master/packages/conventional-changelog-conventionalcommits/src/constants.js)). Teams that release on `chore(deps)` without a writer change get an npm version whose GitHub notes are empty ([mattbun](https://mattbun.io/posts/semantic-release-dependabot/)). The old `"hidden": false` snippet is the previous preset shape.

## A feat subject for every dep major will outrank the right patch

The plan on the table is retitle, then `gh pr merge --merge --subject` set to `fix(deps)` for a dependency patch or minor, `feat(deps)` for a dependency major, and `feat(deps)!:` when a label says breaking, with the repository default changed so the pull-request title becomes the merge subject. That plan fixes a real hole: the current command sets `--body` and leaves the headline as `Merge pull request #N`, and a conventional `--subject` is what makes the merge commit itself releasable ([gh pr merge](https://cli.github.com/manual/gh_pr_merge)). It is the squash-era pattern moved onto `--merge`. Under the contract table it is the wrong automatic encoding, because semantic-release will take the higher of the merge commit and the Dependabot commit. A plugin that correctly scores an SDK major or a `fastify-plugin` major as patch loses to `feat(deps)` on the merge commit, and the package ships a minor. One subject also cannot describe every layer of a stack that lands as a single history operation, `gh stack merge` does not document forwarding a per-pull-request headline, and a merge queue ignores `commitHeadline` and `commitBody` ([Merging stacked pull requests](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-stacked-pull-requests), [EnablePullRequestAutoMergeInput](https://koki-develop.github.io/magidoc-github-pages-example/types/EnablePullRequestAutoMergeInput)). The trailer is still on each bot commit in all of those cases.

Keep **`--subject` for the human raise alone**. On a held row (prom-client major, a package rename, or a diff the table cannot decide), the workflow passes a single-line subject the human chose: `fix(deps):` for a package patch, `feat(deps):` for a package minor, `feat(deps)!:` with a short `BREAKING CHANGE:` body written by the workflow when the contract actually broke. The body stays that one sentence. It is never the Dependabot pull-request body. Confident rows pass no `--subject`, leave the default `Merge pull request #N` headline, and let the plugin publish from the YAML and the `package.json` diff. Keep the repository merge title on the default merge message, so a retitle stays off the merge commit when someone merges in the UI. Retitle on `pull_request_target` remains a review aid, refreshed on `synchronize` because Dependabot regenerates commits, and it is not an input to the analyzer. Auto-merge only when every member is `none` or `patch`, no member is a prom-client `semver-major` or a rename, and the diff does not change `engines`, the Fastify peer, or the `fp()` string. A security fix ranked patch auto-merges on that same test so `^1.x` receives it. A security fix that fails the test waits with row 5, and the advisory for consumers who stay on 1.x says the fix requires 2.x when no compatible backport exists.

Keep `commit-message.prefix` at `chore(deps)` and `prefix-development` at `chore(deps-dev)`, so the stock rules keep dev commits and ordinary chores quiet and the plugin is the only automatic bump. Leave the coarse `{ type: 'chore', scope: 'deps', release: 'patch' }` rule out. That rule would publish lockfile-only commits, SDK majors, and prom-client majors at a single level, and it has to be ordered after the `false` rule or it publishes nothing. Whether this repo's prefix plus `include: scope` yields `chore(deps):` or `chore(deps)(deps):` was not confirmed on a live commit; the plugin should not parse the subject, which makes that ambiguity irrelevant. In the release-notes preset, list a `chore` / `deps` entry with an effect that shows the commit before the catch-all hidden `chore`, and copy `feat`, `fix`, and `perf` back into `presetConfig.types` because a custom list replaces the defaults. Expect the Dependabot commit, not the merge commit, to be the changelog line for a confident row. A human `feat(deps)!:` merge commit will appear as well, which is the breaking note users need, and the version is still one max for that push.

Split groups in Dependabot where the table can produce two ranks that must not share a commit. `monitoring-tools` should keep majors out, which it already does. `fastify-ecosystem-major` should stay a separate pull request so a peer shrink is not glued to a plugin-helper patch. `aws-ecosystem` stays mixed while every AWS level maps to the same package rank; the engines diff is what escalates a member, and that check works inside one commit. `security-critical` matches none of the three production dependencies, so either point it at a real production pattern or stop treating the name as a severity. `typescript-ecosystem`, `jest-testing`, `linting-formatting`, `build-utilities`, and the Actions groups stay `none` and should not be given a releasing prefix. Before the plugin is trusted, run it on one single-dependency commit and one grouped commit from this repository. The June 2026 grouped render used as a sample was truncated before `Signed-off-by`, and no commit from this repo was parsed in the research. `update-type` and `dependency-name` are the fields that have been stable; `dependency-version` is not, and the "Updates `name` from A to B" lines are the fallback when both versions are required.

## Conclusion

The digit ladder and the merge-subject encoding fail together. Once a dependency major is allowed to be a package patch, any automatic `feat(deps)` subject becomes a false minor, because the analyzer keeps the higher level and a second plugin cannot put it back. The durable source of truth is the bot commit that merge, retarget, regenerate, and a stack landing all preserve, read by one plugin that is also the conventional-commit analyzer, with `--subject` reserved for the pull requests the table refuses to publish. Scalar `update-type` and the group name are the wrong aggregators for that plugin: they collapse a mixed group to the highest dependency digit, and this package's mixed groups are full of digits that do not change the rank.

What changes in practice is where human judgment sits. It sits on prom-client majors, on a module rename, and on any diff that moves `engines` or the Fastify peer, and it sits there as a conventional subject written at merge time. It does not sit on every SDK weekday, every `fastify-plugin` major, or every devDependency. A stack that merges as one push still produces one version, equal to the max in that range, so a security patch that must reach `^1.x` has to be its own pull request onto `main` before it shares history with a package major. That split is what keeps the compatible line alive.
