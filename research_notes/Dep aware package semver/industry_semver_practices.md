# Dependency-driven semver for published npm libraries

Scope: published libraries (not applications), as of November 2026. Package shape used when applying the guidance: `peerDependencies.fastify` of `^4 || ^5`, runtime dependencies `@aws-sdk/client-cloudwatch`, `fastify-plugin`, and `prom-client`. The maintainer rule of thumb under critique is: patch or minor dependency bump → package patch; major dependency bump or a new feature → package minor; breaking features or a “substantial” non-compatible dependency → package major.

Primary specifications do not define a dependency-type matrix. What follows separates spec text, npm docs, OpenJS-adjacent maintenance docs, tool defaults, and maintainer opinions. Opinions are labeled as such.

## When does a dependency bump require a package release at all?

### Takeaway

A library release is required only when the published artifact changes in a way consumers can observe, which for an unbundled library means `package.json` ranges (or shipped source), not the lockfile. In-range lockfile bumps and devDependency-only bumps usually do not justify a release. A production-dependency range change does, and the semver FAQ treats that release as compatible (patch or minor) unless the public API changed.

### Cited Findings

- SemVer 2.0.0 requires a declared public API. After 1.0.0, patch is only for backward-compatible bug fixes (“an internal change that fixes incorrect behavior”), minor is for backward-compatible public API additions and MUST also be used when deprecating public API, and minor MAY be used for “substantial new functionality or improvements” inside private code. Major MUST be used for any backward-incompatible public API change. Once a version is released, its contents MUST NOT be modified; any modification MUST be a new version. — [semver.org](https://semver.org/)
- SemVer FAQ, “What should I do if I update my own dependencies without changing the public API?”: the update “would be considered compatible since it does not affect the public API.” Whether the library release is patch or minor “depends on whether you updated your dependencies in order to fix a bug or introduce new functionality.” The FAQ adds that new functionality would “usually” involve additional code, “in which case it’s obviously a minor level increment.” — [semver.org](https://semver.org/)
- The same FAQ says other packages that depend on the same libraries “should have their own dependency specifications and the author will notice any conflicts.” It does not require a library release merely because an upstream package published something new. — [semver.org](https://semver.org/)
- npm’s semantic-versioning doc recommends a new publish “every time you make significant updates,” and says: “If you introduce a change that breaks a package dependency, we strongly recommend incrementing the version major number.” The only bump table on that page is the generic one: patch = backward-compatible bug fixes, minor = backward-compatible new features, major = changes that break backward compatibility. The page does not define “breaks a package dependency” or split runtime, peer, and dev dependencies. — [npm: About semantic versioning](https://docs.npmjs.com/about-semantic-versioning/)
- npm documents `dependencies` as packages required in production and `devDependencies` as packages only needed for local development and testing. It tells publishers not to put test harnesses or transpilers in `dependencies`. `peerDependencies` express compatibility with a host tool “while not necessarily doing a require of this host,” and are “usually referred to as a plugin.” — [npm: package.json](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/)
- Node.js package-maintenance guidelines (OpenJS ecosystem, `nodejs` org): `package-lock.json` “will not be published into the registry” and “is only intended to be used for development purposes.” Consequence stated in the same doc: a lockfile means “you may be testing your package with a different set of dependency versions than your users will be using.” `npm-shrinkwrap.json` is published and, for a library, “may prevent deduplication.” Caret ranges are the recommended default so dependents accept new minor and patch releases of dependencies. In-range updates are applied with `npm update` without editing the version specifier; out-of-range updates require editing `package.json`. — [Node.js dependency management guidelines](https://github.com/nodejs/package-maintenance/blob/main/docs/dependency-management-guidelines.md)
- Same Node.js doc: dropping support for specific Node.js versions “is normally considered a breaking change,” and a dependency upgrade that forces that drop “will force you to release a new major version of your package as well.” — [Node.js dependency management guidelines](https://github.com/nodejs/package-maintenance/blob/main/docs/dependency-management-guidelines.md)
- OpenJS Foundation Security WG: do not publish automatically on merge to the default branch. A human must choose “it’s time to publish a new version, here’s the version number it will use” (git tag or explicit workflow). Dependabot and Renovate are recommended as detectors, not as the publisher. For a package with no build step, audit runtime dependencies (`dependencies` and `peerDependencies`); `devDependencies` need auditing when they generate published code. — [OpenJS secure releases](https://github.com/openjs-foundation/security-wg/blob/main/docs/Secure_Releases/secure-releases.md)
- semantic-release maintainer reply (2019) on Dependabot `chore(deps)` commits that update production dependencies: the Angular convention does not release on `chore`. Recommended fix is to configure the bot to emit `fix` commits for dependency updates, “what greenkeeper.io does,” so a release happens. The issue is closed as support, not as “do not release.” — [semantic-release#1329](https://github.com/semantic-release/semantic-release/issues/1329)
- semantic-release commit-analyzer maintainers (issue discussion): updating a GitHub Action “should not result in any notable changes for your consumers, so not releasing for that update would follow our recommendation.” Production dependency commits should use the `fix` type under the Angular preset so they do release. Dependabot’s `prefix` / `prefix-development` is the documented way to get that split. — [semantic-release/commit-analyzer#536](https://github.com/semantic-release/commit-analyzer/issues/536)
- GitHub documents Dependabot `commit-message.prefix` for all commits and `prefix-development` for the Development dependency group (supported for npm). `include: scope` appends `deps` or `deps-dev`. Defaults follow patterns already detected in the repo; GitHub does not itself assign a semver level to the library. — [Dependabot configuration options](https://docs.github.com/en/code-security/dependabot/dependabot-version-updates/configuration-options-for-the-dependabot.yml-file)
- A widely copied practice note: Dependabot’s `build(deps)` does not match semantic-release’s default `fix`/`feat` rules. Setting production prefix to `fix` and development prefix to `build`, or a commit-analyzer rule `{ "type": "build", "scope": "deps", "release": "patch" }`, makes production dependency updates a patch release. Scope `deps-dev` stays unreleased. — [Getting Dependabot and semantic-release to Play Nice](https://mattbun.io/posts/semantic-release-dependabot/)
- On the SemVer issue tracker, a detailed (non-spec) comment: if the library can consume the new dependency build with no rebuild and no code change, “no new release” and “let your consumer decide.” A release exists to force consumers onto the new dependency. A private adaptation that preserves the public API is a patch; exposing new public API is a minor; a breaking public API, including re-exported types that broke, is a major. — [semver/semver#148](https://github.com/semver/semver/issues/148)

### Inferences

- For this package, a Dependabot PR that only refreshes `package-lock.json` inside existing `^` ranges of `@aws-sdk/client-cloudwatch`, `fastify-plugin`, or `prom-client` does not change what downstream installers resolve. Publishing would not deliver the bump. No release.
- A PR that edits `dependencies` in `package.json` (raises a floor, or switches major) does change the published manifest, so SemVer rule 3 requires a new version if that manifest is published. The level is a separate question.
- A PR that only edits `devDependencies` does not affect consumers’ installs. OpenJS’s audit split and semantic-release’s `deps-dev` practice agree: no release, unless the dev dependency changes emitted build output that is published.
- Security fixes follow the same gate. If the patched upstream version is already inside the published range, consumers get it by updating their own lockfile; a library republish with the same range does not force that. Raising the floor above the vulnerable release is what makes the library release carry the fix, and that raise is what must be versioned.
- semantic-release will not inspect whether the dependency moved patch, minor, or major. A `fix(deps)` commit becomes a package patch even when the dependency moved a major. Humans retitle to `feat` or `BREAKING CHANGE` when the API effect is larger. That is a tooling default, not the spec.
- The user rule’s first clause (patch or minor dep → package patch) matches this release gate only after a release is warranted. It is too coarse if read as “every such bump ships a patch.” Lockfile-only and devDependency bumps ship nothing.

### Gaps

- npm’s sentence about a change that “breaks a package dependency” is not defined further in the current docs. No npm RFC turned up in this pass that maps dependency bump kind to package bump kind.
- No OpenJS document states “release the library on production dependency updates.” The security-WG doc says the opposite about automation: a human picks the version at publish time. The Node.js package-maintenance doc covers ranges and lockfiles, not “must you publish.”
- This pass did not measure how often popular libraries actually publish on lockfile-only Dependabot merges versus manifest edits.

## How should runtime deps vs peerDependencies vs devDependencies differ?

### Takeaway

Dev dependencies usually cause no release. Runtime dependencies are internal unless types or behavior leak, so a compatible library bump (often patch) is the spec default. Peer dependencies are part of the install contract: widening the range is a compatible feature, and dropping a previously accepted peer version is treated as a breaking change by SemVer-repo discussion and by Fastify’s one-major-per-host practice.

### Cited Findings

- SemVer FAQ treats “my own dependencies” as not the public API. Patch versus minor follows bugfix versus new functionality, and new functionality is expected to come with additional code. — [semver.org](https://semver.org/)
- SemVer spec item 7: minor MAY be incremented for substantial new functionality or improvements “within the private code,” even without a public API addition. That is optional (`MAY`), unlike the `MUST` for public API additions and deprecations. — [semver.org](https://semver.org/)
- npm: `dependencies` are production requirements; `devDependencies` are not installed for someone who only depends on your package; `peerDependencies` declare the host a plugin is compatible with. As of npm 7, peers are installed by default; a conflicting peer requirement can make the tree fail to resolve. — [npm: package.json](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/)
- 8 Hobbies synthesis (blog, June 2024, updated June 2025), explicitly an interpretation of SemVer rather than the spec: runtime or optional dependency bumps are internal and “usually should only lead to incrementing PATCH,” unless the package wraps an API that changed, or the package “benefits substantially” (the blog cites the spec’s minor-for-private-improvements clause, for example a significant performance improvement). Dev dependency bumps “should not usually even bump the version,” unless they change generated output (TypeScript declarations, Vite build). Peer dependency: widening the range (example `^1 || ^2`) is a MINOR; requiring a new peer major is a MAJOR; raising a peer minor floor is a package MINOR; raising a peer patch floor is a package PATCH. The blog’s rationale for the last two is downgrade safety, not the SemVer FAQ. — [8 Hobbies](https://8hob.io/posts/semantic-versioning-npm-packages-after-dependency-update/)
- SemVer GitHub issue #502, maintainer-side comments (not spec text): “any peer dep change that removes a previously valid version from being valid is a major/breaking change. Peer deps are part of the public API.” A later comment in the same thread: it is breaking “if they have to do anything besides update your package.” The example discussed is `redux-form` moving its React peer from `^16.4.0` to `^16.8.0`, argued as a major of redux-form because consumers stuck on React 16.4 would break, even though 16.4 to 16.8 is not a React major. — [semver/semver#502](https://github.com/semver/semver/issues/502)
- On semver#148, Jordan Harband (2019): upgrading a peer by a major “is absolutely a breaking change, because it forces consumers to upgrade the peer dep.” He goes further: “npm peer deps are part of your api — adding one is breaking, as is bumping it at all — not just a major.” A later commenter in the same thread disputes that any peer floor movement is major if application behavior is unchanged. — [semver/semver#148](https://github.com/semver/semver/issues/148)
- Same issue, earlier comment (Eddie Garmon, 2013, opinion): hiding the dependency’s types means the library bump reflects only the library’s own API edits (patch if the public API is unchanged, minor if public features are added). Exposing any types from the dependency that themselves had breaking changes means the library ships a major. — [semver/semver#148](https://github.com/semver/semver/issues/148)
- OpenJS secure-release guidance groups `dependencies` and `peerDependencies` together as the runtime audit set, and excludes `devDependencies` when nothing is generated into the published tarball. — [OpenJS secure releases](https://github.com/openjs-foundation/security-wg/blob/main/docs/Secure_Releases/secure-releases.md)
- Fastify’s own plugin helper documents version lines against Fastify majors: “the v4.x series of this module covers Fastify v4”; v2 and v3 of `fastify-plugin` cover Fastify v3; v1 covers Fastify v2. The `fastify` option passed to `fp()` is a semver range checked against the host. — [fastify-plugin README](https://github.com/fastify/fastify-plugin/)
- Official Fastify plugins publish an explicit compatibility table and a new plugin major per Fastify major. `@fastify/sensible`: plugin `>=6` with Fastify `^5`, plugin `^5` with Fastify `^4`, plugin `^4` with Fastify `^3`. `@fastify/bearer-auth`: plugin `^10` with Fastify `^5`, `^8` with `^4`. Both say that if a Fastify version is out of support, the corresponding plugin versions in the table are too. — [@fastify/sensible](https://github.com/fastify/fastify-sensible), [@fastify/bearer-auth](https://github.com/fastify/fastify-bearer-auth/)
- Fastify LTS: each major is supported at least six months, then security fixes for six months after the next major. The schedule lists 4.0.0 released 2022-06-08 and end of LTS 2025-06-30; 5.0.0 released 2024-09-17 with end of LTS still TBD as of the current docs page. The same page states that breaking changes are sometimes shipped as a Fastify minor for security, always documented, and that consumers who want to avoid those can pin with `~` while accepting the vulnerability. — [Fastify LTS](https://fastify.dev/docs/latest/Reference/LTS/)

### Inferences

- Three different contracts, three different bumps:
  - `devDependencies`: no package release unless published artifacts change.
  - Runtime `dependencies` (`@aws-sdk/client-cloudwatch`, `fastify-plugin`, `prom-client` if they stay encapsulated): SemVer FAQ default is a compatible release, patch when the point is a bugfix or a private adaptation, minor only when the library grows public API or elects the spec’s optional “substantial private improvement” minor. The dependency’s own major number is not the signal.
  - `peerDependencies` (`fastify`): the range is the compatibility contract. Adding `^5` beside an existing `^4` removes no previously valid host, so it is a minor (8 Hobbies; consistent with #502’s “removes a previously valid version” test). Deleting `^4` and leaving only `^5` removes a valid host, so it is a major (#502, Harband, and Fastify’s own plugin majors).
- #502 and Harband conflict with the 8 Hobbies table on peer floor raises inside one major (`^16.4.0` → `^16.8.0`, or `fastify` `^4.0.0` → `^4.28.0`). The issue discussion calls that a major because some previously installable hosts become invalid. The blog calls a peer-minor floor raise a package minor. The spec FAQ never mentions peers. For a plugin, the #502 test matches how installers actually fail, and it is the stricter reading.
- The user rule collapses runtime and peer into one ladder. That matches neither the FAQ nor Fastify. A Fastify peer drop is not a package minor. A runtime dependency’s patch or minor is not automatically a package patch release either, because it may not require a release at all.
- `fastify-plugin` is a runtime helper, not the host. Consumers of a Fastify plugin do not select `fastify-plugin` the way they select `fastify`. Bump it like an encapsulated runtime dependency unless a new major of `fastify-plugin` changes registration behavior or forces a narrower Fastify host than the peer range claims. The README’s series notes show the helper’s majors have historically been tied to Fastify majors, so a major bump of `fastify-plugin` has to be checked against the `^4 || ^5` peer rather than assumed to be internal.

### Gaps

- The SemVer specification still has no normative rule that names `peerDependencies`. #502 is discussion, and it disagrees with the 2024–2025 blog table on intra-major peer floor raises.
- This pass did not inventory `fastify-plugin`’s current npm major (whether v5/v6 declare a `fastify` peer). The README still documents series-to-Fastify mapping; one downstream commit claims `fastify-plugin@6` has no peerDependencies and that the `fp()` range is metadata Fastify checks. That commit was not treated as the project’s policy. — [opena2a commit](https://github.com/opena2a-org/agent-identity-management/commit/b20a51bfbf17acb89595400c157d5da0a82af47b)

## When should a major dependency bump cause a package major vs only a minor?

### Takeaway

A dependency major causes a package major when it breaks the library’s public API, re-exported types, documented behavior, supported runtime, or accepted peer versions. If none of those move, the spec calls the library release compatible: patch by default, minor if the library adds API or chooses to advertise a substantial private improvement. It does not call for a package minor merely because the dependency’s major digit changed.

### Cited Findings

- Spec: major MUST track backward-incompatible public API changes. Minor MAY track substantial private improvements. FAQ: a dependency update that does not change the public API is compatible, and the patch/minor choice tracks bugfix versus new functionality, “usually” with additional code for the minor case. — [semver.org](https://semver.org/)
- semver#148 opinion that is the clearest case split in the official tracker: dependency major that is fully internalized and worked around with no public API change → library patch; same, but the library adds public features to fill the gap → library minor; library must remove public features, or it re-exports the dependency types that broke → library major. If no code change is required, “no new release.” — [semver/semver#148](https://github.com/semver/semver/issues/148)
- A conflicting opinion in that same thread (wcooley, “gestalt”): any dependency change that means a previously valid environment is no longer valid, including “a new version of that dependency must be installed,” should be a major, because dependents who also depend on the old version can break. Other comments disagree and warn that a spurious library major strands the previous major on the old, buggy dependency, since fixes then only land on the new major. — [semver/semver#148](https://github.com/semver/semver/issues/148)
- 8 Hobbies: a runtime dependency major is still a library PATCH unless an exception applies (wrapped API changed, or substantial benefit worth a minor). A peer major that replaces the old range is a library MAJOR. Widening to include a new peer major while keeping the old one is a library MINOR. — [8 Hobbies](https://8hob.io/posts/semantic-versioning-npm-packages-after-dependency-update/)
- Node.js package-maintenance: a dependency upgrade that drops Node.js versions the library used to support forces a major of the library, because dropping Node is “normally considered a breaking change.” — [Node.js dependency management guidelines](https://github.com/nodejs/package-maintenance/blob/main/docs/dependency-management-guidelines.md)
- npm’s only related normative-sounding sentence is the major bump when you “introduce a change that breaks a package dependency,” paired with the generic backward-compatibility row. It does not say “dependency major → your minor.” — [npm: About semantic versioning](https://docs.npmjs.com/about-semantic-versioning/)
- semantic-release’s recommended encoding of a production dependency update is a `fix` commit, which releases a patch, including when the only change is the dependency. A major upstream does not automatically become a library minor in that system. — [semantic-release#1329](https://github.com/semantic-release/semantic-release/issues/1329), [commit-analyzer#536](https://github.com/semantic-release/commit-analyzer/issues/536)

### Inferences

- The user rule “major dep OR new feature → package minor” mixes two signals the spec keeps apart. A new feature of this package is a minor (spec item 7, MUST if it is public API). A major of a runtime dependency is not, by itself, a feature. Calling it a minor over-tells consumers there is new API, and under-tells them if the major actually broke types, peers, or engines.
- Correct split for a runtime major of an encapsulated dependency: package patch if behavior and support matrix hold (FAQ + #148 private-workaround case); package minor only if this package adds API or deliberately ships a substantial private improvement; package major if the public contract breaks.
- Correct split for a peer major: replacing `fastify: ^4 || ^5` with `^5` is a package major. Adding a future `^6` while keeping `^4 || ^5` is a package minor. That second case is the one time a “major dependency” event is only a package minor, and it is a range widen, not a floor replacement.
- The “spurious major strands bugfixes” comment in #148 is the practical argument against bumping the library major for every upstream major that did not touch the library API. Fastify’s model avoids that trap by maintaining separate plugin majors, each still able to receive fixes, rather than by folding a host major into a minor of one line.

### Gaps

- There is no spec example that uses the words “package minor because a dependency went major.” The minor-for-major-dep step in the user rule is not found in semver.org, npm’s bump table, or the semantic-release recommendation.
- How often maintainers retitle Dependabot major-bump PRs from `fix` to `feat!` was not measured.

## How do Fastify plugins, AWS SDK consumers, and Prometheus client wrappers typically handle this?

### Takeaway

Fastify official plugins cut a new plugin major for each Fastify major and leave older plugin majors in place for older hosts. The AWS SDK for JavaScript v3 does not use the minor digit as SemVer, ships breaking and engine changes inside 3.x, and wrappers cannot republish on every weekday SDK release. prom-client has used real majors for breaking metric APIs and Node drops; in 2026 the Prometheus project renamed it to `@prometheus-io/client` with further breaking changes, which is a dependency-identity change for wrappers.

### Cited Findings

- Fastify official plugins encode host support as a table of plugin major → one Fastify major, and they tell users that an unsupported Fastify line means the matching plugin line is unsupported too. Examples: `@fastify/sensible` 6.x/5.x/4.x for Fastify 5/4/3; `@fastify/bearer-auth` 10.x/8.x for Fastify 5/4. — [@fastify/sensible](https://github.com/fastify/fastify-sensible), [@fastify/bearer-auth](https://github.com/fastify/fastify-bearer-auth/)
- `fastify-plugin` documents the same shape for itself: v4 of the helper covers Fastify v4, older helper majors cover older Fastify majors. Plugin metadata includes a `fastify` semver range. — [fastify-plugin README](https://github.com/fastify/fastify-plugin/)
- Fastify LTS end for v4 is 2025-06-30. v5, released 2024-09-17, is the supported major in the current table (EOL listed as TBD). Breaking security fixes may land as Fastify minors and are documented; `~` opts out. — [Fastify LTS](https://fastify.dev/docs/latest/Reference/LTS/)
- A 2026 Fastify docs change removed ecosystem plugins whose latest `peerDependencies.fastify` or `dependencies.fastify` does not intersect Fastify `^5`. `devDependencies.fastify` was ignored on purpose: “it is not a runtime contract.” 228 of 299 listed plugins declared no Fastify range at all, so v5 compatibility was “indeterminate from package.json alone.” — [fastify commit b7eb53e](https://github.com/fastify/fastify/commit/b7eb53e41e1db355ddd2a04f2fbbfca7962a7bd9)
- In 2018, a Fastify maintainer (Matteo Collina) described the plugin policy as moving ranges to `^1.0.0` so plugins “will support only one major, and they will require a new release when we bump the major.” — [fastify#763](https://github.com/fastify/fastify/issues/763)
- AWS SDK and Tools maintenance policy (cross-SDK): versions are X.Y.Z where X is the major. “Major versions are introduced when public interfaces (e.g. classes, methods, types, etc.), behaviors, or semantics have changed.” Applications “need to be updated” for a new major. Separately: “AWS reserves the right to stop support for an underlying dependency without increasing the major SDK version.” — [AWS SDKs and Tools maintenance policy](https://docs.aws.amazon.com/sdkref/latest/guide/maint-policy.html)
- AWS SDK for JavaScript v3 README: “Our releases usually happen once per weekday. Each release increments the minor version, e.g. 3.200.0 → 3.201.0.” Node floors also moved on minor releases inside v3: v3.201.0+ requires Node ≥ 14, v3.567.0+ requires Node ≥ 16, v3.723.0+ requires Node ≥ 18, v3.968.0+ requires Node ≥ 20. A 2026 TypeScript support-window table is published in the same README. — [aws-sdk-js-v3 README](https://github.com/aws/aws-sdk-js-v3/blob/main/README.md)
- AWS maintainer on the JS SDK (kuhe, 2024-02-22, issue #5818), after a peerDependency change that users called breaking: “Due to some wording in the existing maintenance policy, we are not releasing changes in adherence to semver.” The stated cause is the product generation “v3” occupying the major component. — [aws-sdk-js-v3#5818](https://github.com/aws/aws-sdk-js-v3/issues/5818)
- Issue #4153 (2022) records repeated breakage inside 3.x and a New Relic agent maintainer’s constraint: instrumentation “affects our customers when they upgrade past the version we support,” and “it is untenable to ship a new version of our aws-sdk instrumentation on every release as the AWS SDK seems to release daily.” — [aws-sdk-js-v3#4153](https://github.com/aws/aws-sdk-js-v3/issues/4153)
- JS SDK v3.974.0 (GitHub issue, maintainers): internal dependencies moved from exact pins to open ranges so different client versions dedupe onto one core runtime. “No changes are needed by AWS SDK users.” Multiple installed copies of the core had been causing TypeScript failures and “subtle runtime bugs such as prototype mismatch and unintended duplication of singleton objects.” — [aws-sdk-js-v3#7686](https://github.com/aws/aws-sdk-js-v3/issues/7686)
- prom-client changelog (majors that are actually breaking): 13.0.0 (2020-12-16) made `registry.metrics()`, `getMetricsAsJSON()`, `getMetricsAsArray()`, and `getSingleMetricAsString()` async, and `clusterMetrics()` callback-only was removed. 14.0.0 (2021-09-18) changed `linearBuckets` so “histogram bucket labels may change.” 15.0.0 (2023-10-09) dropped Node 10, 12, 14, 17, and 19. npm’s `prom-client` page, as retrieved in this pass, still listed 15.1.3 (2024-06-27) as the latest 15.x release. — [prom-client changelog](https://github.com/siimon/prom-client/blob/master/CHANGELOG.md), [npm prom-client](https://registry.npmjs.org/prom-client)
- The same changelog’s 0.16.0 entry dated 2026-08-24, also present on `prometheus/client_js`, says this is the first release as a Prometheus subproject and “the package is renamed from `prom-client` to `@prometheus-io/client`.” Breaking notes include: cluster IPC message types renamed, so a primary and its workers must run the same major; drop Node 16, 18, 20, 21, and 23; internal `hashMap` replaced by `LabelMap` for subclassers; counter exemplars report value rather than delta; `MetricType` becomes a string union. Gauges “no longer initialize to zero” is listed under Unreleased breaking notes in that file. — [Prometheus client_js changelog](https://github.com/prometheus/client_js/blob/main/CHANGELOG.md)

### Inferences

- A library that peers `fastify` `^4 || ^5` is choosing the community widen pattern, not the official-plugin pattern. Official plugins would have shipped that as two majors (one line left on Fastify 4, one line requiring Fastify 5). Keeping both in one version is valid only while the plugin’s code and its `fp()` range truly accept both. Fastify 4 has been out of LTS since 2025-06-30, so the `^4` half is compatibility, not a supported Fastify line. Dropping `^4` later is a package major, not a minor, even if the motivation is “Fastify 4 is EOL.”
- Fastify’s own exception (breaking security fixes in a minor, documented) means a plugin range of `^4` or `^5` can pick up a host minor that is not strictly compatible. Plugin authors do not cut a plugin major for each Fastify minor. They document the host range and let the host’s release notes carry the exception.
- For `@aws-sdk/client-cloudwatch`, the dependency’s minor digit is a calendar counter, not a SemVer minor. The user rule “patch/minor dep → package patch” would label an SDK minor that raises Node from 18 to 20 (3.968.0) as a routine patch. Node.js package-maintenance says a library that adopts that floor and thereby drops Node 18 must ship a library major. The user rule “major dep → package minor” almost never fires for this SDK, because breaking changes have been landing without a 4.0.0. Wrappers should ignore the SDK’s digit and test the library’s behavior, types, and `engines`.
- New Relic’s position is the release gate for AWS consumers: do not publish the wrapper on each SDK weekday. Publish when the wrapper’s supported SDK floor, Node floor, or public instrumentation behavior must change. v3.974.0’s dedupe fix is a reason a wrapper might raise its minimum inside 3.x without calling that a breaking change of the wrapper, as long as `engines` and the public options stay valid. Two copies of the SDK in one process are a known failure mode, so a floor raise that still overlaps the app’s client version is safer than a floor that forces a second major.
- For `prom-client`, majors 13, 14, and 15 are “real” majors: async metrics, histogram label changes, and Node drops. A wrapper that calls `registry.metrics()` and sends the string on the wire broke on 13.0.0 unless it started awaiting. That is a package major of the wrapper if the wrapper’s HTTP contract or documented Node support changed, and a patch or minor only if the wrapper hid the change completely. The 2026 rename to `@prometheus-io/client` is not a routine major inside the same package name. Switching the runtime dependency to the new name, or re-exporting classes whose `instanceof` identity moved, is substantial. Staying on `prom-client@15` with an in-range bump is not, until the unreleased gauge-default break (or a later 15.x break) shows up in behavior the wrapper documents.
- `fastify-plugin` should be handled with the Fastify table, not the AWS calendar and not the prom-client type surface. Consumers rarely import it. Its major matters when it changes which Fastify versions the plugin can register on.

### Gaps

- No Fastify RFC was found that tells third-party plugins to use one major per Fastify major. The evidence is the official plugins’ tables, Collina’s 2018 comment, and the 2026 ecosystem doc sweep. Community plugins that peer `^4 || ^5` in a single version are common enough that the docs sweep had to check intersection with `^5` rather than assuming one major.
- No maintained “AWS SDK wrapper semver policy” from AWS was found. The consumer evidence is the New Relic comment and the SDK’s own non-SemVer admission.
- The npm registry snippet for `prom-client` still showed 15.1.3 as latest, while the GitHub changelog documents a 2026-08-24 rename release under 0.16.0 / `@prometheus-io/client`. This pass did not re-query the registry for `@prometheus-io/client` to confirm that 0.16.0 is what installers resolve today. Treat the rename as documented by the project changelog, and confirm the dist-tag before switching the dependency.

## What heuristics distinguish a substantial non-compatible dependency from a routine major?

### Takeaway

“Substantial” means the library’s consumers must change something other than the library version, or a previously supported environment stops working. The upstream project’s major digit is a hint only when that project actually follows SemVer. Routine majors are internalized, behavior-preserving dependency upgrades that do not narrow peers, engines, or exported types.

### Cited Findings

- Spec test: incompatible public API → major (MUST). Compatible bugfix → patch (MUST). New compatible public API, or a deprecation → minor (MUST). Substantial private improvement → minor (MAY, not MUST). Dependency updates that do not change the public API stay in the compatible band. — [semver.org](https://semver.org/)
- Peer test from the SemVer issue tracker: a peer change that removes a previously valid version is breaking. More generally, it is breaking if consumers must do anything besides update your package. — [semver/semver#502](https://github.com/semver/semver/issues/502)
- Re-export test from the same tracker: breaking changes in types that the library exposes are breaking changes of the library; the same break, fully hidden, is a patch if the public API survives. — [semver/semver#148](https://github.com/semver/semver/issues/148)
- Platform test from Node.js maintainers: dropping Node.js versions is normally a breaking change of your package, including when a dependency upgrade is what forces the drop. — [Node.js dependency management guidelines](https://github.com/nodejs/package-maintenance/blob/main/docs/dependency-management-guidelines.md)
- Counterexample to “trust the upstream digit,” AWS JS SDK: weekday minors, explicit maintainer statement that releases do not adhere to SemVer, Node engine floors moved at 3.201 / 3.567 / 3.723 / 3.968, and a cross-SDK policy note that dependency support can be dropped without a major. — [aws-sdk-js-v3 README](https://github.com/aws/aws-sdk-js-v3/blob/main/README.md), [aws-sdk-js-v3#5818](https://github.com/aws/aws-sdk-js-v3/issues/5818), [AWS maintenance policy](https://docs.aws.amazon.com/sdkref/latest/guide/maint-policy.html)
- Counterexample the other way, prom-client: majors called out as breaking in the changelog (async registry methods, histogram bucket labels, Node drops), so those majors are evidence, not ceremony. The 2026 package rename is a separate, larger contract change. — [prom-client changelog](https://github.com/siimon/prom-client/blob/master/CHANGELOG.md)
- Fastify’s documented exception: some breaking security fixes ship as minors and must be called out in release notes. A downstream library does not treat every Fastify minor as substantial, but it cannot assume a Fastify minor is always API-compatible either. — [Fastify LTS](https://fastify.dev/docs/latest/Reference/LTS/)
- Duplicate-install hazard specific to this SDK: mismatched client versions used to install multiple core runtimes, with prototype and singleton bugs. A “routine” bump that splits or unifies that runtime can be user-visible even when the wrapper’s functions did not change. — [aws-sdk-js-v3#7686](https://github.com/aws/aws-sdk-js-v3/issues/7686)

### Inferences

Heuristics that mark a dependency change as substantial (package major), applied to this package:

- The new `fastify` peer range no longer matches some version the old `^4 || ^5` range accepted. Dropping 4, or raising a minimum so that 4.x installs fail, is substantial. Adding `|| ^6` is not.
- `fp()` metadata or `fastify-plugin` behavior rejects a Fastify major the peer range still advertises. The published peer would be a lie; that is substantial.
- The wrapper’s public types include AWS client inputs, outputs, or errors, and those types changed incompatibly. Digit on the SDK does not matter; the type break does.
- Adopting an `@aws-sdk/client-cloudwatch` floor at or above 3.968.0 drops Node 18 (or a later floor drops Node 20) while the library still claims the old engine. That is substantial even though the SDK called it a minor.
- The wrapper’s documented metrics text, label names, or sync-versus-async handler behavior changes because prom-client 13/14/15 (or the 2026 client) changed under it. Async `metrics()`, changed histogram buckets, exemplar value versus delta, and gauge default 0 are substantial if any of them cross the plugin’s HTTP or metric contract.
- The dependency package name changes (`prom-client` → `@prometheus-io/client`) and consumers can observe the new module, whether through re-exports, `instanceof`, or peer instructions.

Heuristics that mark the same kind of bump as routine (no release, or a package patch; minor only if the spec’s optional private-improvement clause is deliberately used):

- Lockfile-only movement inside a caret already published. Consumers were already allowed to install it.
- `devDependencies` only, with no change to published JavaScript or types.
- A prom-client or fastify-plugin bump that stays inside the current major, passes the plugin’s tests, and does not change status codes, metric names, options, or the Fastify peer.
- An AWS SDK 3.x bump that does not move `engines`, does not change wrapper options or exported types, and does not force a second copy of the SDK core beside the version the host app already uses. Do not cut a release per weekday. If a floor raise is published only to pick up a bugfix and the support matrix is unchanged, the FAQ says package patch, not package minor.
- A true major of an encapsulated dependency where the library does not use the removed API, does not re-export its types, and does not narrow peers or engines. #148 calls that a patch. The user rule calls it a package minor. The spec side of that disagreement is the patch (or no release if the range did not have to move).

The user rule is right that breaking features of this package are a major, and it is right that a merely internal patch or minor of a SemVer-following runtime dependency is not a major. It is wrong in the middle rung: a dependency major is not a package minor by default, and “substantial” is not a synonym for “the dependency maintainers incremented X.” Substantial means a consumer-visible contract change: peer set, engines, exported types, or documented behavior. For `@aws-sdk/client-cloudwatch`, that contract change often arrives disguised as a minor. For `fastify`, it arrives when the peer range shrinks, which official plugins then express as their own major. For `prom-client`, it arrives on changelog-documented majors and on the 2026 rename, not on every 15.x patch.

### Gaps

- No source gives a numeric or checklist definition of the spec’s word “substantial” for private improvements. It remains a maintainer judgment, and it is optional.
- This pass did not review this repo’s own exports to see whether AWS types or prom-client classes are part of the public surface. The heuristics above are conditional on that fact.
- Peer-floor policy inside a single Fastify major (`^4.0.0` to `^4.29.0`) is unsettled between #502 (any removed version is major) and day-to-day plugin releases (often a minor or patch). Not resolved by Fastify’s LTS doc.
