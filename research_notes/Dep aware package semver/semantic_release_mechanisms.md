# Semantic-release mechanisms for dependency-driven package versions

Grounded on a library published with semantic-release (`@llevintza/fastify-prometheus-metrics`). Installed versions checked in this repo: `semantic-release` 25.0.9, `@semantic-release/commit-analyzer` 13.0.1, `conventional-changelog-conventionalcommits` 10.4.1, `micromatch` 4.0.8. Behavior below was executed against those copies, and it matches the current analyzer source.

The package’s `.releaserc.js` passes root-level `preset: 'conventionalcommits'`, `releaseRules`, and `parserOpts` into plugins. In semantic-release 25.0.9 that merge is real: plugin config is `{ ...rootOptions, ...pluginEntryConfig }`, so the root rules are what `@semantic-release/commit-analyzer` and `@semantic-release/release-notes-generator` see. — [semantic-release `lib/plugins/normalize.js`](https://github.com/semantic-release/semantic-release/blob/master/lib/plugins/normalize.js)

Dependabot’s configurable commit prefix cannot encode semver severity. `commit-message.prefix` is one string for all updates, `prefix-development` is a second string for dev dependencies only, and `include` accepts only `scope` (`deps` or `deps-dev`). — [GitHub Dependabot `commit-message`](https://docs.github.com/en/code-security/dependabot/dependabot-version-updates/configuration-options-for-the-dependabot.yml-file#commit-message)

Severity lives in the commit body trailer Dependabot already writes, for example `update-type: version-update:semver-major` inside an `updated-dependencies:` YAML block. Grouped updates repeat that key once per dependency. — [dependabot/fetch-metadata#632](https://github.com/dependabot/fetch-metadata/pull/632); example commits [github/dependabot-action@e3b93d7](https://github.com/github/dependabot-action/commit/e3b93d7525c51995ad7ba3867bde88d45e837999), [operaton@d6ab729](https://github.com/operaton/operaton/commit/d6ab729afe07ce6a23c26472d1426e4a0fa1b7e6), [BlackF1re/atlantian@779579f](https://github.com/BlackF1re/atlantian/commit/779579ff41d56108d573e7abfe8b102c2ccd937b)

## What releaseRules / subject / scope patterns can distinguish dep patch vs minor vs major?

### Takeaway

Scope and type can separate `chore(deps)` from `chore(deps-dev)` and can map every production dep bump to a single release level. They cannot tell a dependency’s patch from its minor or major. Subject globs cannot compare versions. Body globs look like they could match `version-update:semver-*`, and they do on a slash-free string, but they do not match a real Dependabot body: micromatch `*` does not cross `/`, and Dependabot bodies contain URLs. The three-way map (dep patch/minor → package patch, dep major → package minor) needs a custom `analyzeCommits` plugin that searches the raw commit message. `parserOpts.noteKeywords` can only mark a commit breaking, which is package major.

### Cited Findings

- Custom `releaseRules` are an array of objects, or a module path whose export is an array. Each object has `release` plus match criteria. Criteria are matched against the conventional-commits parse (`type`, `scope`, `subject`, `header`, `body`, `footer`, and the rest of the parsed commit). String criteria are micromatch globs. If any custom rule matches, its `release` is used. Default rules run only when no custom rule matches (`undefined`). — [commit-analyzer README](https://github.com/semantic-release/commit-analyzer?tab=readme-ov-file); [load-release-rules.js](https://github.com/semantic-release/commit-analyzer/blob/master/lib/load-release-rules.js); [index.js](https://github.com/semantic-release/commit-analyzer/blob/master/index.js)
- Valid `release` values are `major`, `premajor`, `minor`, `preminor`, `patch`, `prepatch`, `prerelease`, `false`, and `null`. A function is rejected: the loader throws unless the value is an array. — [default-release-types.js](https://github.com/semantic-release/commit-analyzer/blob/master/lib/default-release-types.js); [load-release-rules.js](https://github.com/semantic-release/commit-analyzer/blob/master/lib/load-release-rules.js)
- Among matching rules, the highest ranked type wins. Rank is index order in `["major", "premajor", "minor", "preminor", "patch", "prepatch", "prerelease"]` (lower index wins). As soon as a match sets `major`, later rules for that commit are not examined. — [analyze-commit.js](https://github.com/semantic-release/commit-analyzer/blob/master/lib/analyze-commit.js); [compare-release-types.js](https://github.com/semantic-release/commit-analyzer/blob/master/lib/compare-release-types.js)
- `release: false` is not in that list, so `indexOf(false)` is `-1`. Comparison treats a falsy current type as “replace me” (`!false === true`), and it treats `-1` as higher than `patch` and `minor` when `false` is the candidate. Measured on commit-analyzer 13.0.1:
  - `{ type: 'chore', scope: 'deps', release: 'patch' }` followed by `{ type: 'chore', release: false }` → `chore(deps)` releases nothing.
  - The same two rules with `false` first → `chore(deps)` is `patch`, `chore(deps-dev)` stays no-release.
  - A `major` match stops the loop, so a later `release: false` does not clear a major.
  - A `false` match does not stop the loop, so a later `patch` or `minor` still replaces it.
  Community writeups that say “last match wins” or “`release: false` clears and stops” describe pieces of this, and they disagree with each other. — measured against `@semantic-release/commit-analyzer` 13.0.1; contradicted in part by [firstsun-dev/git-files-sync@b4b1808](https://github.com/firstsun-dev/git-files-sync/commit/b4b180874d2689b85ef06d4bebd3ac364c3723b0) (“last matching rule wins”) and [udibo/juniper#78](https://github.com/udibo/juniper/pull/78) (“`release: false` clears the release type and stops iteration”)
- Default rules, used only on no match, are `{ breaking: true, release: 'major' }`, revert → patch, `feat` → minor, `fix` → patch, `perf` → patch. `chore` is absent, so an unmatched `chore` does not release. A matching `{ type: 'chore', release: false }` blocks that fallthrough, including for a `chore` commit that carries a breaking note. — [default-release-rules.js](https://github.com/semantic-release/commit-analyzer/blob/master/lib/default-release-rules.js); [index.js](https://github.com/semantic-release/commit-analyzer/blob/master/index.js)
- The conventionalcommits preset parses `type(scope): subject` and `type(scope)!: subject`. Header pattern: `/^(\w*)(?:\((.*)\))?!?: (.*)$/`. A `!` before the colon produces a `BREAKING CHANGE` note whose text is the subject. `breaking: true` rules match when `commit.notes.length > 0`, so any parsed note is “breaking,” not a separate minor/patch channel. — [conventionalcommits parser.js](https://github.com/conventional-changelog/conventional-changelog/blob/master/packages/conventional-changelog-conventionalcommits/src/parser.js); [constants.js `BREAKING_HEADER_PATTERN`](https://github.com/conventional-changelog/conventional-changelog/blob/master/packages/conventional-changelog-conventionalcommits/src/constants.js); [analyze-commit.js](https://github.com/semantic-release/commit-analyzer/blob/master/lib/analyze-commit.js); [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)
- `noteKeywords` (this repo sets `BREAKING CHANGE` and `BREAKING CHANGES`) only feed that breaking path. They cannot assign `minor` or `patch`. — [commit-analyzer README `parserOpts`](https://github.com/semantic-release/commit-analyzer?tab=readme-ov-file)
- Dependabot `include: scope` yields scope `deps` or `deps-dev`. A glob `deps*` matches both `deps` and `deps-dev` (measured). Exact scope `deps` does not match `deps-dev`. — [Dependabot `include`](https://docs.github.com/en/code-security/dependabot/dependabot-version-updates/configuration-options-for-the-dependabot.yml-file#commit-message); measured with micromatch 4.0.8 via commit-analyzer 13.0.1
- Published recipes stop at one level: `{ type: 'build', scope: 'deps', release: 'patch' }` or `{ type: 'chore', scope: 'deps', release: 'patch' }`, leaving `deps-dev` unmatched. Dependabot prefix `fix` plus `prefix-development: chore` is the other one-level approach (every production bump becomes a fix/patch). — [mattbun, “Getting Dependabot and semantic-release to Play Nice”](https://mattbun.io/posts/semantic-release-dependabot/); [framerslab/agentos-skills `release.config.cjs`](https://github.com/framerslab/agentos-skills/blob/master/release.config.cjs)
- micromatch 4.0.8: `*` matches a single-line `update-type: version-update:semver-major`. `*` does not match across `/`. A realistic Dependabot body (release-note URLs plus the YAML block plus newlines) does not match `*semver-major*`, `**semver-major**`, or `**`. `String` inclusion of `version-update:semver-major` is true for that same body. On that message, conventional-commits-parser left the YAML in `body` and put only `Signed-off-by:` in `footer`. A bare unindented `update-type:` line before `Signed-off-by` was parsed as `footer` with an empty `body` instead. — measured with micromatch 4.0.8 and `conventional-changelog-conventionalcommits` 10.4.1; micromatch slash rules are documented in [micromatch](https://github.com/micromatch/micromatch)
- The Express/Atom lines inside default rules include `{ component: 'deps', release: 'patch' }`. Those fields are not set by the conventionalcommits parser, so they do nothing for `chore(deps)` commits. — [default-release-rules.js](https://github.com/semantic-release/commit-analyzer/blob/master/lib/default-release-rules.js)
- `conventional-changelog-conventionalcommits` 10.4.1 hides `chore`, `build`, `ci`, `docs`, `style`, `refactor`, and `test` from notes (`effect: 'hidden'`). Hiding is independent of whether the analyzer releases. A type entry with no `effect` is treated as `bump` and is shown. `findTypeEntry` returns the first entry with the same type whose scope is unset or equal, so a scoped `chore`/`deps` entry has to be listed before a catch-all hidden `chore`. Passing `presetConfig.types` replaces the whole default list. The writer also un-hides a commit whose body or footer matches `/release-as:\s*.../`, but commit-analyzer never reads `release-as`. — [constants.js](https://github.com/conventional-changelog/conventional-changelog/blob/master/packages/conventional-changelog-conventionalcommits/src/constants.js); [writer.js](https://github.com/conventional-changelog/conventional-changelog/blob/master/packages/conventional-changelog-conventionalcommits/src/writer.js); [utils.js `isTypeEffect`](https://github.com/conventional-changelog/conventional-changelog/blob/master/packages/conventional-changelog-conventionalcommits/src/utils.js)

### Inferences

- For this repo’s rule list, a new `{ type: 'chore', scope: 'deps', release: 'patch' }` has to be placed after `{ type: 'chore', release: false }`. Placed before it, `false` replaces `patch` and the bump stays unpublished. That single rule publishes every production dep bump as a package patch, including dependency majors. It does not implement dep-major → package minor.
- A body-glob rule such as `{ type: 'chore', scope: 'deps', body: '*version-update:semver-major*', release: 'minor' }` works on a toy message with no URLs and fails on a normal Dependabot message. It is not an actionable config for this repo.
- Exact scope `deps` plus three raw-message checks in a custom plugin is the mechanism that can encode dep patch → package patch, dep minor → package patch, dep major → package minor. `BREAKING CHANGE:` / `type!:` remains the existing package-major signal, and it is not implied by `update-type: version-update:semver-major`.
- `chore(deps-dev)` should stay on the `release: false` path if dev dependencies must not ship a new library version. Exact scope `deps` does that; scope glob `deps*` does not.
- If production dep commits start releasing, changelog config has to un-hide that type/scope or the GitHub release and `CHANGELOG.md` can ship with an empty body while npm still gets a new version. The old blog snippet `"hidden": false` is the previous preset shape; 10.4.1 uses `effect`.

### Gaps

- No Dependabot setting was found that changes the commit type or scope based on semver-major vs semver-minor vs semver-patch. The 2026 docs only document `prefix`, `prefix-development`, and `include: scope`.
- Whether a security-update commit honors `commit-message` is disputed. The 2026 configuration page says a defined `commit-message` applies to all commit messages. An older guide says security updates ignore it and stay on `build(deps)`. This pass did not inspect a 2026 security-update commit. — [Dependabot `commit-message`](https://docs.github.com/en/code-security/dependabot/dependabot-version-updates/configuration-options-for-the-dependabot.yml-file#commit-message); contradicted by [mattbun](https://mattbun.io/posts/semantic-release-dependabot/)

## Can custom analyzer plugins inspect Dependabot metadata, PR labels, or commit body trails?

### Takeaway

A custom `analyzeCommits` plugin can read the full git commit message, including the `updated-dependencies` / `update-type` trailer. semantic-release does not pass Dependabot’s API object or pull-request labels into the analyzer. Labels can be consulted only if the plugin calls the GitHub API itself. `releaseRules` cannot be a function, so the semver decision cannot live in a rule module; it has to live in the plugin (or in a commit message rewritten before merge).

### Cited Findings

- `analyzeCommits(pluginConfig, context)` is the step that returns `major`, `minor`, `patch`, or a falsy “no release.” `context.commits` comes from `git log <lastTag>..<head>` with the full message (`%B`). — [Plugins lifecycle](https://semantic-release.org/foundation/plugins/); [semantic-release `lib/git.js` `getCommits`](https://github.com/semantic-release/semantic-release/blob/master/lib/git.js); [commit-analyzer index.js](https://github.com/semantic-release/commit-analyzer/blob/master/index.js)
- If several plugins implement `analyzeCommits`, semantic-release keeps the highest of `["patch", "minor", "major"]` (higher index wins). A falsy result does not outrank a real level. A second plugin can raise a commit the stock analyzer ignored; it cannot lower a `major` the stock analyzer already returned. — [semantic-release `lib/definitions/plugins.js`](https://github.com/semantic-release/semantic-release/blob/master/lib/definitions/plugins.js); [constants.js `RELEASE_TYPE`](https://github.com/semantic-release/semantic-release/blob/master/lib/definitions/constants.js)
- Before analysis, semantic-release drops commits whose message matches `/\[skip release]|\[release skip]/i`. `[skip ci]` is not in that expression. — [plugins.js preprocess](https://github.com/semantic-release/semantic-release/blob/master/lib/definitions/plugins.js)
- The stock analyzer then parses each message with `conventional-commits-parser`. Rules see parsed fields, not GitHub labels, not the Dependabot API, and not a structured `update-type` field. — [commit-analyzer index.js](https://github.com/semantic-release/commit-analyzer/blob/master/index.js)
- `releaseRules` as a path must export an array of rule objects. A function export throws. — [load-release-rules.js](https://github.com/semantic-release/commit-analyzer/blob/master/lib/load-release-rules.js); [README “External package / file”](https://github.com/semantic-release/commit-analyzer?tab=readme-ov-file)
- semantic-release’s own description of the data it uses: it “works purely from the commit history, not from pull requests.” — [semantic-release discussion #4082](https://github.com/semantic-release/semantic-release/discussions/4082)
- Dependabot’s stable machine-readable trailer is the YAML block (`dependency-name`, `dependency-type`, `update-type: version-update:semver-patch|semver-minor|semver-major`, and on grouped PRs `dependency-group`). `dependency-version` was missing from grouped commits in 2024 and is present on 2026 examples; `update-type` was already present in the 2024 report. The block does not include an old version, and it does not include a “this bump breaks consumers” flag beyond the semver class. — [dependabot-core#8217](https://github.com/dependabot/dependabot-core/issues/8217); [fetch-metadata#632](https://github.com/dependabot/fetch-metadata/pull/632)
- `dependabot/fetch-metadata` is a GitHub Action that exposes `update-type` on the pull request. It is not a semantic-release plugin. — [fetch-metadata#632](https://github.com/dependabot/fetch-metadata/pull/632)
- An inline plugin object in the `plugins` array is loaded as a plugin (semantic-release 25.0.9 registers each function on a plain object). A local `analyzeCommits` can sit next to `@semantic-release/commit-analyzer`. — [semantic-release `lib/plugins/index.js`](https://github.com/semantic-release/semantic-release/blob/master/lib/plugins/index.js)

### Inferences

- The plugin that matches this repo’s desired map should scan `commit.message` (the raw `%B` text) for `update-type: version-update:semver-major|semver-minor|semver-patch`, ignore messages whose subject scope is `deps-dev`, and return `minor` if any included production update is `semver-major`, otherwise `patch` if any is `semver-minor` or `semver-patch`, otherwise `null`. Returning `null` for ordinary `feat` / `fix` commits leaves those to the stock analyzer. The highest of the two plugins is the release.
- Pull-request labels are not on the Dependabot commit. With merge commits, the merge commit subject contains `Merge pull request #<n>`, and the Dependabot commit contains the trailer and usually not the PR number. `context.commits` is a flat list; the stock git fields used here are hash, full message, tags, and committer date, not parent SHAs. Correlating a label on PR `#n` with the YAML commit is custom GitHub API work inside the plugin, and it is brittle. Encoding the override in a commit that survives the merge is the path that stays inside semantic-release’s model.
- A “this dependency break is a package major” signal is not in `update-type`. Practical encodings that a plugin can see after a merge (not a squash) are a second commit on the PR (`fix!:` / `BREAKING CHANGE:` footer, or a dedicated trailer the plugin understands) or a rewritten commit message. Labels alone are invisible after merge.
- Because a plugin can only raise the level relative to the other analyzer, a false major from `{ breaking: true, release: 'major' }` cannot be corrected by the dependency plugin. Keep package-major detection in one place.

### Gaps

- This pass did not find an official context field for PR labels, check-run annotations, or Dependabot metadata beyond text that is already in the git message.
- It did not verify that `git-log-parser`’s default fields in semantic-release 25.0.9 include parent SHAs. The explicit field overlay in `lib/git.js` sets hash, message, tags, and committer date.

## How do merge commits vs squash merges affect what semantic-release sees?

### Takeaway

`gh pr merge --merge` keeps the Dependabot commit, and that commit is what the analyzer scores. The merge commit itself (`Merge pull request #N from ...`) does not match conventionalcommits and does not release. A squash throws away the Dependabot commit; semantic-release sees only the squash message. If that message drops the `updated-dependencies` block, the severity trailer is gone.

### Cited Findings

- semantic-release analyzes commits reachable on the release branch since the last release tag. A merge commit is just another commit in that range. Maintainer statement: when a merge commit is created, semantic-release analyzes the merged commits and ignores the merge commit, because the merge commit is not a conventional message. The tool does not have a separate merge mode. — [semantic-release PR #794](https://github.com/semantic-release/semantic-release/pull/794); [commit-analyzer issue #146](https://github.com/semantic-release/commit-analyzer/issues/146); [discussion #4082](https://github.com/semantic-release/semantic-release/discussions/4082)
- `getCommits` uses `git log <from>..<to>`, which lists commits reachable from the new head and not from the last tag, including commits brought in by a merge. — [semantic-release `lib/git.js`](https://github.com/semantic-release/semantic-release/blob/master/lib/git.js)
- Measured with the conventionalcommits parser from 10.4.1: subject `Merge pull request #12 from org/dependabot/npm_and_yarn/foo-2.0.0` and body `chore(deps): bump foo from 1.2.3 to 2.0.0` yields `type` undefined. `analyzeCommit` returns undefined for it (no release from that commit). The preset parser does not set `mergePattern`. The branch commit `chore(deps): ...` is a normal conventional commit and is analyzed on its own. — [parser.js](https://github.com/conventional-changelog/conventional-changelog/blob/master/packages/conventional-changelog-conventionalcommits/src/parser.js); [troubleshooting: squashed commits](https://github.com/semantic-release/semantic-release/blob/master/docs/support/troubleshooting.md)
- Squash merges replace the branch commits with one new commit. If that message is not conventional, semantic-release ignores the change. The project’s guidance is to rewrite the squash message into a conventional message, and to squash only a single self-contained change. — [troubleshooting.md](https://github.com/semantic-release/semantic-release/blob/master/docs/support/troubleshooting.md)
- GitHub’s squash commit uses the PR title as the suggested subject; the body is chosen at merge time (title only, title plus description, or title plus commit details, depending on repository defaults and the person merging). A breaking change on a squash has to be in that one message (`feat!:` or a `BREAKING CHANGE:` footer). The angular preset does not treat `!` as breaking; conventionalcommits does. — [semantic-release issue #2339](https://github.com/semantic-release/semantic-release/issues/2339); [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)
- Discussion #4030: merge commits showed up in notes only when the message was parsed as a conventional type. With a normal “Merge pull request” subject they are excluded. A bad `parserOpts` / preset resolution can change that. — [discussion #4030](https://github.com/semantic-release/semantic-release/discussions/4030)

### Inferences

- This repo’s `gh pr merge --merge` path is the one that preserves `update-type` without an extra rewrite. The analyzer will see one releasable Dependabot commit plus one ignored merge commit. That is not two releases.
- Switching to squash would make the PR title (`chore(deps): bump ...`) the only subject, which is enough for a single “all deps are patch” rule, and it is not enough for a three-way map unless the squash body still contains `updated-dependencies`. Repository squash-message settings can omit that body.
- Setting `parserOpts.mergePattern` is optional here. The default conventionalcommits parse already fails the merge subject. A merge pattern that accidentally captured the PR title out of the body could start treating merge commits as conventional and double-count a change that is also present as its own commit.

### Gaps

- This pass did not record the exact default squash body produced by `gh pr merge --squash` in 2026 (title only vs title plus Dependabot PR body). The merge path this repo uses does not depend on that default.

## Are there existing community plugins for dependency-driven releases?

### Takeaway

No maintained semantic-release plugin showed up that reads Dependabot `update-type` and maps it to patch vs minor vs major. The community pattern is a one-line `releaseRules` entry that treats production dep commits as a package patch. The only Dependabot-named semantic-release plugin found notifies Dependabot about a private package publish; it does not choose a version.

### Cited Findings

- Common public configs map `build(deps)` or `chore(deps)` to `patch` and leave `deps-dev` alone, then un-hide that type in the release-notes preset so the changelog is not blank. — [mattbun](https://mattbun.io/posts/semantic-release-dependabot/); [agentos-skills release.config.cjs](https://github.com/framerslab/agentos-skills/blob/master/release.config.cjs); [DEV Community guide using `prefix: fix`](https://dev.to/kengotoda/a-complete-guide-to-use-dependabot-with-semantic-release-and-vercel-ncc-for-github-actions-230p)
- `@amanda-mitchell/semantic-release-notify-dependabot` 1.0.8 (last published 2022-04-04, about 24 weekly downloads at search time) calls Dependabot after a private npm publish. Its README lists `packageManager`, `packageRoot`, and `packageName`. It has no `analyzeCommits` configuration and no `update-type` handling. — [npm `@amanda-mitchell/semantic-release-notify-dependabot`](https://www.npmjs.com/package/@amanda-mitchell/semantic-release-notify-dependabot)
- `dependabot/fetch-metadata` parses `update-type` for workflow `if:` conditions on the pull request. It does not run inside semantic-release. — [fetch-metadata#632](https://github.com/dependabot/fetch-metadata/pull/632)
- One public config uses a custom type `dependabot` → patch. That only works if commit messages actually use the type `dependabot`. Dependabot’s own prefix options do not emit that type unless `prefix` is set to it, and then every update shares that type. — [ssdx-cli `release.config.mjs`](https://github.com/sopra-steria-salesforce/ssdx-cli/blob/refs/heads/dependabot/npm_and_yarn/npm-production-51ea169939/release.config.mjs); [Dependabot `commit-message`](https://docs.github.com/en/code-security/dependabot/dependabot-version-updates/configuration-options-for-the-dependabot.yml-file#commit-message)

### Inferences

- The implementable options for this library are (1) a local `analyzeCommits` plugin in `.releaserc.js` or a file next to it, or (2) a coarser `releaseRules` scope rule that publishes every `chore(deps)` as a package patch. Option (2) does not meet dep-major → package minor.
- `fetch-metadata` is still useful on the PR workflow (auto-merge policy, labels) and does not replace the post-merge analyzer.

### Gaps

- npm and GitHub searches in this pass did not turn up a plugin whose README claims “semver-major dependency → minor package release.” Absence from those searches is not a proof that no unpublished gist exists.

## What are failure modes (false majors, no-release when expected, double bumps)?

### Takeaway

The current rule `{ type: 'chore', release: false }` is why Dependabot merges do not release, and a more specific dep rule placed above it will keep not releasing. A generic `{ breaking: true, release: 'major' }` plus this repo’s release commit message (`chore(release): <version> [skip ci]` plus the generated notes) will parse the previous breaking note again and can cut another major. semantic-release applies the single highest level across the whole range since the last tag; it does not add a patch and a minor together, and a merge commit plus its Dependabot commit do not count twice when the merge subject stays `Merge pull request #N`.

### Cited Findings

- Measured with this repo’s current `releaseRules` and the conventionalcommits parser: `chore(deps)` and `chore(deps-dev)` for patch, minor, and major dependency bumps all return `false`. `chore(deps)!` and a `chore(deps)` body that contains a `BREAKING CHANGE:` footer also return `false`, because every breaking rule in the file also requires type `feat`, `fix`, `perf`, or `refactor`. `fix!:` returns `major`. `feat:` returns `minor`. `chore(major):` returns `major` because `{ scope: 'major', release: 'major' }` is reached and `major` stops the loop before `{ type: 'chore', release: false }`. — measured on commit-analyzer 13.0.1 against `.releaserc.js`; rule algorithm in [analyze-commit.js](https://github.com/semantic-release/commit-analyzer/blob/master/lib/analyze-commit.js)
- The same measurement: a release commit `chore(release): 1.2.3 [skip ci]` whose body is changelog text containing a line `BREAKING CHANGE: removed foo` parses a breaking note. Under the current rules the result is still `false` (type `chore`). Under a rule set that has `{ breaking: true, release: 'major' }` first, the result is `major`, and the loop never reaches the chore `false` rule. This repo’s `@semantic-release/git` message is `chore(release): ${nextRelease.version} [skip ci]\n\n${nextRelease.notes}`. — [analyze-commit.js](https://github.com/semantic-release/commit-analyzer/blob/master/lib/analyze-commit.js); git message in the repo `.releaserc.js`
- `[skip ci]` does not remove a commit from analysis. `[skip release]` and `[release skip]` do. — [plugins.js](https://github.com/semantic-release/semantic-release/blob/master/lib/definitions/plugins.js)
- Across commits, the analyzer keeps one level: the highest of the per-commit results. Two patch commits do not become `0.0.2` extra; a patch dep commit and a `feat` in the same range become one minor. — [commit-analyzer index.js](https://github.com/semantic-release/commit-analyzer/blob/master/index.js)
- A grouped Dependabot commit has several `update-type` lines and still one parsed commit, so it has one release type. If both `semver-patch` and `semver-major` appear, a plugin that takes the max will return the major mapping only. — [atlantian grouped commit](https://github.com/BlackF1re/atlantian/commit/779579ff41d56108d573e7abfe8b102c2ccd937b); [fetch-metadata#632](https://github.com/dependabot/fetch-metadata/pull/632)
- `chore` notes are hidden by the conventionalcommits writer unless `types` is overridden. Teams that turn on dep releases without changing the writer get a published version whose GitHub release notes omit the dependency commits (mattbun: notes stay blank until `build` is un-hidden). — [constants.js](https://github.com/conventional-changelog/conventional-changelog/blob/master/packages/conventional-changelog-conventionalcommits/src/constants.js); [mattbun](https://mattbun.io/posts/semantic-release-dependabot/)
- Order bugs already shipped in other repos: a catch-all `{ type: 'chore', release: false }` after `{ type: 'chore', scope: 'deps', release: 'patch' }` swallowed the patch, and the release was “no release” until the false rule was removed or moved above the dep rule. — [udibo/juniper#78](https://github.com/udibo/juniper/pull/78); [firstsun-dev/git-files-sync@b4b1808](https://github.com/firstsun-dev/git-files-sync/commit/b4b180874d2689b85ef06d4bebd3ac364c3723b0)
- Replacing the default rules and forgetting `{ breaking: true, release: 'major' }` drops breaking detection for any commit the custom list matches. A custom list that matches `chore(deps)` as patch will not consult the default breaking rule for that commit. — [index.js](https://github.com/semantic-release/commit-analyzer/blob/master/index.js); [agentos-skills comment citing commit-analyzer v13.0.1](https://github.com/framerslab/agentos-skills/blob/master/release.config.cjs)
- Squash commit messages that are not conventional are ignored entirely, so a dependency merge that should have released produces no release. — [troubleshooting.md](https://github.com/semantic-release/semantic-release/blob/master/docs/support/troubleshooting.md)

### Inferences

- No release when a dep release was expected, for this repo specifically: `chore` → `false` matches `chore(deps)` and `chore(deps-dev)`. Fixing it with a scope rule requires the `false` rule to stay above the dep rules, not below them. Deleting the chore `false` rule also lets unmatched chores fall through to defaults (still no release for a normal chore) but a chore that contains a breaking note would then become a major via the default breaking rule.
- False package major: adding an unqualified `{ breaking: true, release: 'major' }` so that `chore(deps)!` or a `BREAKING CHANGE:` footer can mean “package major” also makes the next `chore(release)` commit a major whenever `nextRelease.notes` still contains that footer text. `[skip ci]` does not stop that second analysis; `[skip release]` in the release commit message does. Leaving breaking rules type-qualified, as the file does today, avoids that loop and also means a dependency break written only as `BREAKING CHANGE:` on a `chore(deps)` commit will not cut a major.
- False package major relative to the desired dep policy: `update-type: version-update:semver-major` is “major of the dependency,” which this project wants as a package minor. Mapping that trailer through `{ breaking: true }` or through `scope: 'major'` would overshoot. `scope: 'major'` already forces a package major for any type, and it wins over the chore `false` rule because `major` aborts the loop.
- Double bump does not come from the merge commit plus the Dependabot commit under the default parser. It does come from (1) the release commit being releasable on the following CI run, or (2) expecting semantic-release to add levels (dep minor mapped to patch, plus a `feat`, plus another dep) instead of taking the max once per tag range.
- Empty notes after a successful publish are likely if `chore` stays `effect: 'hidden'`. That looks like a failed release in GitHub and is a normal npm publish from semantic-release’s point of view.
- A grouped PR that mixes a dependency major and a dependency patch will publish at the higher mapped level only. Splitting groups in Dependabot is the way to get separate package releases; the analyzer will not split one commit.

### Gaps

- No 2026 measurement here of how often Dependabot pastes the upstream changelog, as opposed to links, into the commit body. A full pasted changelog that contains a `BREAKING CHANGE:` line at footer position would be parsed as a breaking note. The sample messages used in this pass (the documented short body plus YAML) did not do that. A prose line `See BREAKING CHANGE: in upstream notes` did not create a note.
- Stacked-PR conflicts caused by the `chore(release)` commit editing `package.json` and `CHANGELOG.md` are a git workflow issue, not an analyzer rule. They were not tested here.
