# Encoding Dependabot severity for semantic-release

Scope is a GitHub Actions + Dependabot + semantic-release stack that must use merge commits (squash disabled), with `GH_TOKEN` and `XOON_NPM_PUBLISH_TOKEN` already available. Desired package bump map: dependency patch or minor → package patch; dependency major → package minor; a human-judged breaking or substantial update → package major. Notes are current as of November 2026.

## What does Dependabot put in PR titles, commits, and bodies today (including groups)?

### Takeaway
Dependabot writes one commit per version-update PR, uses that commit subject as the PR title, and stores machine-readable per-dependency metadata in the commit body. Grouped updates do not list each bump in the subject; they say “bump the GROUP group…” and put each package’s `update-type` in a YAML trailer, plus “Updates `name` from A to B” lines.

### Cited Findings
- `commit-message` changes both commit messages and PR titles. Parameters are only `prefix` (max 50 characters), `prefix-development`, and `include`. A prefix that ends in a letter, number, `)`, or `]` gets a colon inserted before the rest of the message; a trailing space suppresses the colon. — [Dependabot options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)
- `include` accepts only `scope`. The prefix is then followed by the dependency class, `deps` or `deps-dev`, not by the package name. npm supports `prefix-development`. — [Dependabot options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)
- The same `commit-message` block also applies to security updates for that manifest, unless `target-branch` sends version updates to a non-default branch. — [Customizing Dependabot pull requests](https://docs.github.com/en/code-security/tutorials/secure-your-dependencies/customizing-dependabot-prs)
- Default text follows commit patterns Dependabot detects in the repo. With no custom prefix, a grouped 2026 npm commit subject is `Bump the npm_and_yarn group across 1 directory with 2 updates`. — [Dependabot options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference); [garm commit e503948, 2026-06-17](https://github.com/cloudbase/garm/commit/e503948c4012d0ef4189f84515153fd1dfd2b89f)
- That grouped commit body contains prose lines `Updates \`form-data\` from 4.0.5 to 4.0.6` and `Updates \`js-yaml\` from 4.1.1 to 4.2.0`, then an `updated-dependencies` YAML list with `dependency-name`, `dependency-version`, `dependency-type`, and `dependency-group` for each package. The page render truncates the trailer with `...` before `Signed-off-by`. — [garm commit e503948](https://github.com/cloudbase/garm/commit/e503948c4012d0ef4189f84515153fd1dfd2b89f)
- A single-dependency commit subject includes both versions (`Bump Microsoft.Playwright from 1.38.0 to 1.39.0`). Its body repeats that sentence, links release notes, then the same YAML trailer with `update-type: version-update:semver-minor`. A grouped commit’s subject does not contain versions; the YAML in that older example had `update-type` and `dependency-group` but not the version. — [dependabot-core #8217](https://github.com/dependabot/dependabot-core/issues/8217)
- `fetch-metadata` treats the YAML block as the stable multi-dependency source and documents `update-type` inside it. “Updates `name` from A to B” lines are a second source that carries both versions. The YAML’s `dependency-version` is the new version only. — [fetch-metadata PR 632](https://github.com/dependabot/fetch-metadata/pull/632)
- Grouped updates are still one commit for the whole group. One-commit-per-dependency inside a group PR was an open feature request, last updated 2024-09-10. — [dependabot-core #8450](https://github.com/dependabot/dependabot-core/issues/8450)
- For grouped PRs, the branch name and PR title are defined by the group `IDENTIFIER`. That identifier must start and end with a letter and may contain letters, `|`, `_`, and `-`. `update-types` can limit a group to `minor`, `patch`, and/or `major`. `applies-to` defaults to version updates; security updates are grouped only when configured. — [Dependabot options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)
- This repo sets npm `prefix: "chore(deps)"`, `prefix-development: "chore(deps-dev)"`, and `include: "scope"`, and splits some groups by `update-types` (`fastify-ecosystem` vs `fastify-ecosystem-major`) while other groups (`aws-ecosystem`, `typescript-ecosystem`, `jest-testing`) mix major, minor, and patch. — `.github/dependabot.yml` in this workspace
- Labels in `dependabot.yml` are static. They do not vary by semver level. — [Dependabot options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)

### Inferences
- With this repo’s prefix plus `include: "scope"`, the documented insertion of `(deps)` / `(deps-dev)` after the prefix likely yields a subject like `chore(deps)(deps): bump …` rather than `chore(deps): bump …`. A conventional-commit parser will not read a double parenthetical as `type(scope)`. Confirm on one real PR before depending on the header.
- The PR body is the long human changelog. The commit body is what survives on `main` and what semantic-release can see. Severity has to be read from the commit trailer or written later into the merge commit. It is not enough that it appears in the PR conversation.
- Group name is a severity signal only when the group’s `update-types` list is a single level. Mixed groups in this repo cannot be classified from the identifier alone.

### Gaps
- The June 2026 grouped commit render was truncated, so this pass did not see whether that exact trailer still contains `update-type` line by line. Older commits and the `fetch-metadata` parser both show `update-type` in that YAML.
- No live commit from this repository was inspected, so the double-scope prefix inference is not confirmed here.

## Can Dependabot commit-message config vary by update-type or group?

### Takeaway
No. `commit-message` is one prefix pair per `updates` entry. Groups have no commit-message field, and nothing in the options reference keys the prefix off `major` / `minor` / `patch`.

### Cited Findings
- The only message knobs are `prefix`, `prefix-development`, and `include: "scope"`. `prefix-development` distinguishes the development dependency group (prod vs dev), and only for bundler, composer, mix, maven, npm, pip, and uv. — [Dependabot options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)
- Group keys are `IDENTIFIER`, `applies-to`, `dependency-type`, `exclude-patterns`, `group-by`, `patterns`, and `update-types`. There is no `commit-message` under a group. — [Dependabot options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference); [Optimizing PR creation](https://docs.github.com/en/code-security/tutorials/secure-your-dependencies/optimizing-pr-creation-version-updates)
- A widely used workaround sets `prefix: "fix"` and `prefix-development: "build"` with `include: "scope"`, so production bumps become `fix(deps):` (package patch) and dev bumps stay non-releasing. That cannot emit `feat` for a dependency major. — [Getting Dependabot and semantic-release to play nice](https://mattbun.io/posts/semantic-release-dependabot/)
- semantic-release’s own maintainers’ advice for dependency releases is to make the tool emit `fix` commits, because Angular `chore` does not release. That advice is also patch-only. — [semantic-release #1329](https://github.com/semantic-release/semantic-release/issues/1329)

### Inferences
- Splitting groups by `update-types`, which this repo already does for Fastify, changes the group name inside an otherwise identical `chore` subject. It does not change the conventional type.
- Two `updates` blocks cannot honestly encode three bump levels for one `package.json` either: the prefix is still a single string per block, and the options reference does not provide a per-update-type message. Even a prod-vs-dev split only yields two prefixes.

### Gaps
- This pass did not re-check the current validator error for two `npm` blocks with the same `directory`. The commit-message schema itself still has no per-group or per-semver switch, which is enough to reject prefix configuration as the mechanism.

## How reliable is dependabot/fetch-metadata for update-type and dependency-group?

### Takeaway
Reliable for the highest semver level in a Dependabot-only PR, and reliable for the group name. Not reliable for “is this breaking for our package,” for previous/new version on grouped PRs, or after any non-Dependabot commit is pushed. Security CVSS fields need a PAT and are off by default.

### Cited Findings
- `update-type` is “the highest semver change being made by this PR,” for example `version-update:semver-major`. Allowed values are the same ones as Dependabot’s `ignore` update types. — [fetch-metadata README (v2.4.0; the public README lists the same outputs)](https://github.com/dependabot/fetch-metadata/)
- A grouped PR that mixes semver levels reports the higher one, so one major inside a group makes `update-type` `version-update:semver-major`. — [Classmethod write-up of grouped metadata](https://dev.classmethod.jp/articles/dependabot-grouped-version-updates-metadata-exploration/)
- `dependency-group` is the group name, or an empty string when the PR is not grouped. The action reads a `dependency-group` key from the commit YAML footer rather than the PR body. — [fetch-metadata README](https://github.com/dependabot/fetch-metadata/); [fetch-metadata PR 396](https://github.com/dependabot/fetch-metadata/pull/396)
- `updated-dependencies-json` is the full per-dependency list. `dependency-names` is comma-separated. `dependency-type` is one of `direct:production`, `direct:development`, `indirect`. — [fetch-metadata README](https://github.com/dependabot/fetch-metadata/)
- `previous-version` and `new-version` were blank for grouped updates when group support shipped (`FIXME` in the v1.6.0 era). Later parsing uses the YAML for the new version and “Updates `name` from A to B” for both versions. The scalar outputs are the wrong interface for a group; use the JSON. — [fetch-metadata compare notes around v1.6.0](https://github.com/dependabot/fetch-metadata/compare/v1.5.1...v2.4.0); [fetch-metadata PR 632](https://github.com/dependabot/fetch-metadata/pull/632)
- By default, outputs are populated only when the PR was opened by Dependabot and contains only Dependabot-created commits. `skip-commit-verification` / `skip-verification` turn that check off. — [fetch-metadata README](https://github.com/dependabot/fetch-metadata/)
- `alert-state`, `ghsa-id`, and `cvss` stay empty unless `alert-lookup: true`, which requires a PAT. `compatibility-score` likewise needs `compat-lookup` and a PAT. There is no output for “breaking change in our public API.” — [fetch-metadata README](https://github.com/dependabot/fetch-metadata/)
- This repo’s auto-merge workflow already consumes `update-type`, `dependency-names`, and `dependency-group` from `dependabot/fetch-metadata@v3` on `pull_request_target`. — `.github/workflows/dependabot-auto-merge.yml`

### Inferences
- For the automatic map, `update-type` (highest) is the right single value: a group that contains a major must become a package minor even if it also contains patches. `updated-dependencies-json` is the audit log and the way to ignore dev-only items.
- Retitling the PR does not clear these outputs, because verification looks at commits, not the title. Pushing an extra commit onto `dependabot/*` does clear them, unless verification is skipped.
- `dependency-type` as one string is ambiguous on a group that mixes production and development packages. Per-item JSON is the reliable form.
- `fetch-metadata` is a good input to a workflow that writes a commit message. It is a bad runtime dependency for semantic-release on `main`, because the release job would be re-deriving data that is already in the commit, and a skipped-verification mode trusts a PR that may no longer be bot-only.

### Gaps
- The raw `main` README fetch returned an empty document; the output list above is from the v2.4.0 README plus the current GitHub README snippet, which matches. A v3.1.0 pin used by Microsoft’s retitle workflow was not diffed line by line against v2.4.0. — [microsoft/physical-ai-toolchain workflow](https://github.com/microsoft/physical-ai-toolchain/blob/main/.github/workflows/dependabot-security-prefix.yml)
- The Classmethod post is a secondary confirmation of “highest semver wins.” The primary wording is the action README.

## With `gh pr merge --merge`, what ends up on main for semantic-release to analyze?

### Takeaway
`--merge` keeps every Dependabot commit and adds one merge commit. semantic-release 25 walks the full `from..to` range, merge commits included, and parses each commit’s full message. The default merge subject is `Merge pull request #N from branch`, which does not release. `--subject` replaces that headline, including when `--auto` only arms the merge. This repo’s current command sets `--body` and does not set `--subject`, so today’s auto-merge commit does not bump.

### Cited Findings
- `gh pr merge --merge` (`-m`) merges the head into the base. `--subject` / `-t` is the merge commit subject. `--body` / `-b` is the body. `--auto` waits until requirements pass. — [gh pr merge](https://cli.github.com/manual/gh_pr_merge)
- The CLI copies `--subject` into GraphQL `commitHeadline` and `--body` into `commitBody` only when those flags are non-empty. With `--auto` it calls `enablePullRequestAutoMerge` and still sends that headline and body. If they are omitted, GitHub uses the default message. — [cli `pkg/cmd/pr/merge/http.go`](https://github.com/cli/cli/blob/trunk/pkg/cmd/pr/merge/http.go)
- `enablePullRequestAutoMerge` documents `commitHeadline` and `commitBody` as the message used when the PR becomes mergeable, and documents that a merge queue ignores both. — [EnablePullRequestAutoMergeInput](https://koki-develop.github.io/magidoc-github-pages-example/types/EnablePullRequestAutoMergeInput); [merge message behavior, checked 2026-10-28](https://lesstep.com/github-pull-requests/errors/merge-message-unexpected/)
- Repository default for a merge commit is a message that includes the PR number and title, for example `Merge pull request #123 from patch-1`. The other choices are the pull request title, or the pull request title and description. API fields are `merge_commit_title` (`PR_TITLE` or `MERGE_MESSAGE`) and `merge_commit_message` (`PR_BODY`, `PR_TITLE`, or `BLANK`). — [Configuring commit merging](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-merging-for-pull-requests); [merge message behavior](https://lesstep.com/github-pull-requests/errors/merge-message-unexpected/)
- semantic-release 25.0.2 loads commits with `git-log-parser` over `` `${from}..${to}` `` and reads the full message (`%B`). The invocation does not pass `--no-merges`. — [semantic-release v25.0.2 `lib/git.js`](https://github.com/semantic-release/semantic-release/blob/v25.0.2/lib/git.js); [v25.0.2 `lib/get-commits.js`](https://github.com/semantic-release/semantic-release/blob/v25.0.2/lib/get-commits.js)
- Maintainers have long distinguished that path from conventional-changelog’s own `--no-merges` filter: analysis sees merge commits and the commits they bring in. A merge commit whose subject is edited away from the `Merge pull request` form is just another message to parse. A default merge commit is not a `fix` or `feat`. — [semantic-release #471](https://github.com/semantic-release/semantic-release/issues/471)
- Root keys in `.releaserc` are passed to every plugin. This repo’s root `releaseRules` therefore reach `@semantic-release/commit-analyzer`. `chore` is `release: false`. `fix` is patch. `feat` is minor. `feat`/`fix`/`perf`/`refactor` with `breaking: true` are major. `scope: major|minor|patch` rules sit after the `fix` and `feat` type rules and before the `chore` rule. `parserOpts.noteKeywords` are `BREAKING CHANGE` and `BREAKING CHANGES`. Preset is `conventionalcommits`. — [semantic-release plugins](https://semantic-release.org/foundation/plugins/); `.releaserc.js` in this workspace
- A custom `releaseRules` entry that matches a type is applied before the default “any breaking commit is major” rule, so a later default does not rescue a type that was already matched. — [commit-analyzer #805](https://github.com/semantic-release/commit-analyzer/issues/805)
- `conventionalcommits` release notes hide `chore` unless the notes config sets that type `hidden: false`. — [mattbun.io notes-generator example](https://mattbun.io/posts/semantic-release-dependabot/)
- The release workflow checks out `main` with `fetch-depth: 0` and runs `yarn semantic-release` on push to `main`, using `XOON_NPM_PUBLISH_TOKEN` as `GITHUB_TOKEN`. — `.github/workflows/ci.yml`
- The auto-merge step runs `gh pr merge "$PR_NUMBER" --merge --auto --body "🤖 Auto-merged safe patch update"` and does not pass `--subject`. — `.github/workflows/dependabot-auto-merge.yml`

### Inferences
- After `gh pr merge --merge`, `main` contains (1) the merge commit and (2) the untouched Dependabot commit reachable from the second parent. semantic-release scores both. Today (1) is not a conventional release commit and (2) is `chore` with `release: false`, so a dependency merge publishes nothing.
- `--subject 'fix(deps): …'` makes the merge commit itself a patch, even while the Dependabot commit stays `chore`. `--subject 'feat(deps): …'` is a package minor. `--subject 'feat(deps)!: …'` with a `BREAKING CHANGE:` footer is a package major under this repo’s rule order. `chore(deps)!:` is not, because `{ type: 'chore', release: false }` matches breaking chore commits too.
- `fix(minor):` is still a patch, because the `fix` rule matches before `scope: minor`. Scope encoding is safe only for a type that has no earlier type rule. `chore(patch)`, `chore(minor)`, and `chore(major)` happen to hit the scope rules first, but they stay `chore` in the changelog.
- Passing the Dependabot PR body through `--body`, or setting `merge_commit_message` to `PR_BODY`, can put upstream changelog lines that start with `BREAKING CHANGE` onto a `fix`/`feat` merge commit and promote it to a package major. The current short `--body` avoids that only because the subject is still the default non-conventional headline.
- Retitling alone does not change either commit semantic-release reads, unless the repo’s default merge title is `PR_TITLE` and the human accepts that default. `gh pr merge` without `--subject` does not use the PR title.
- Release runs once per push to `main`. One merge therefore produces at most one version, equal to the highest matching commit in that range. A `chore` commit cannot cancel a `fix` merge commit.

### Gaps
- v25 `lib/plugins/pipeline.js` was not re-read. If a second `analyzeCommits` plugin is added, confirm whether the core keeps the highest result or the last non-null one before relying on two plugins. A single plugin that both parses conventional commits and the Dependabot trailer avoids that question.
- The conventional-commits preset’s `mergePattern` was not re-read. It matters only for subjects that still start with `Merge pull request`. A `--subject` of `fix(deps):` does not look like that pattern.

## How do stacked PR bases complicate merge-commit messaging and release analysis?

### Takeaway
A stack lands as one history operation from the bottom up, then GitHub rebases the next PR onto the trunk. A merge subject written only for the top PR, or only at the moment a human merges that PR, does not describe the lower layers. Dependabot’s own “rebase” regenerates its commits and will not preserve an amended message. Extra commits also make `fetch-metadata` go blank and, by default, stop Dependabot from rebasing.

### Cited Findings
- A GitHub stack is a chain of PRs whose bases point at the branch below, landing on one trunk. Merging is bottom-up. Merging a PR also merges every unmerged PR below it, “as a single operation, ordered from the bottom up.” You cannot merge a middle PR by itself. After that, the next PR is automatically rebased onto the stack base. The stack must be linear or GitHub requires “Rebase stack,” which creates new signed commits. — [Merging stacked pull requests](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-stacked-pull-requests); [Stack code changes](https://docs.github.com/en/pull-requests/tutorials/stack-code-changes-in-pull-requests)
- `gh stack merge` merges every PR up to the one you name, all or nothing. Stack sync rebases with `--force-with-lease` when the trunk moved. When GitHub retargets a stack, it changes the base and does not rebase; `sync`/`rebase` then drop the old base’s commits. — [Stacked pull requests CLI](https://docs.github.com/en/pull-requests/reference/stacked-prs-cli-commands)
- Ordinary (non-stack) PRs whose base branch is merged and deleted are retargeted to the merged PR’s base instead of being closed. That behavior dates to May 2020. — [Pull request retargeting](https://github.blog/changelog/2020-05-19-pull-request-retargeting/)
- API merges of stacks must use the asynchronous merge API. — [Merging stacked pull requests](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-stacked-pull-requests)
- Dependabot’s rebase is not `git rebase`. It reruns the update against the target branch and does not keep the previous commit history. — [dependabot-core #2882](https://github.com/dependabot/dependabot-core/issues/2882)
- `rebase-strategy` defaults to rebasing when the schedule runs, a closed PR is reopened, `target-branch` changes, or the PR conflicts after a push to the target. `disabled` stops that, with a 30-day caveat for PRs that were already open. — [Dependabot options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)
- Extra commits on a Dependabot branch stop rebasing unless the message contains `[dependabot skip]`, `[skip dependabot]`, `[dependabot-skip]`, or `[skip-dependabot]`. — [Managing Dependabot pull requests](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/manage-your-dependency-security/manage-dependabot-prs)
- Workflows triggered by Dependabot on `push`, `pull_request`, `pull_request_review`, and `pull_request_review_comment` get a read-only `GITHUB_TOKEN` and do not receive Actions secrets. `permissions:` can widen the token. Secrets still have to be Dependabot secrets for those events. `pull_request_target` is the documented way to reach normal Actions secrets. The `fetch-metadata` README also warns that a `pull_request_target` run whose PR user is `dependabot[bot]` can still see a read-only `GITHUB_TOKEN` and no secrets; that sentence conflicts with the troubleshooting doc’s recommendation to use `pull_request_target` for secrets. — [Troubleshooting Dependabot on GitHub Actions](https://docs.github.com/en/code-security/reference/supply-chain-security/troubleshoot-dependabot/dependabot-on-actions); [2021 changelog](https://github.blog/changelog/2021-02-18-github-actions-workflows-triggered-by-dependabot-prs-will-run-with-read-only-permissions/); [fetch-metadata README](https://github.com/dependabot/fetch-metadata/)
- A merge queue ignores `commitHeadline` and `commitBody`. — [EnablePullRequestAutoMergeInput](https://koki-develop.github.io/magidoc-github-pages-example/types/EnablePullRequestAutoMergeInput)

### Inferences
- If several Dependabot PRs are one GitHub stack, merging the top of a contiguous slice lands every lower PR in the same history operation. semantic-release then sees one push (or one range) and emits one version: the maximum severity in that range. Encoding that lives only on the top PR’s merge subject drops the lower PRs’ severities. Encoding that lives in each Dependabot commit is still there after the stack lands.
- Separate package versions require separate pushes to `main`. A stack merge will not cut an intermediate patch release before a later minor.
- Retargeting after the parent merges is safe for a PR title and for Dependabot’s regenerated YAML. It is fatal for an amended commit message and for a merge commit that was created by merging the child into the parent branch: Dependabot’s next regenerate throws that history away, and until then `fetch-metadata` sees a non-bot commit and returns empty outputs, which fails the auto-merge job.
- `gh pr merge --subject` on a child whose base is another Dependabot branch writes the conventional subject onto the parent branch, not onto `main`. The parent’s later merge is a different commit. If that later merge uses the default headline, the child’s subject is an intermediate commit semantic-release will still score if it remains reachable. If Dependabot regenerates the parent, that intermediate commit disappears.
- `GH_TOKEN` on the existing `pull_request_target` workflow can retitle and call `gh pr merge`. It should not be used to push rewritten commits to `dependabot/*`. The release token is a different secret and only runs after the merge is already on `main`.

### Gaps
- The stack-merge doc says “a single operation” and “ordered from the bottom up in the resulting history” but does not say whether that is one merge commit or one merge commit per layer. Plan for “every layer’s commits are visible to one release calculation.”
- `gh stack merge`’s docs do not say it forwards a per-PR `commitHeadline`. Do not assume a pre-set `--subject` survives a UI or `gh stack merge`.
- The `pull_request_target` secret warning in the `fetch-metadata` README and GitHub’s troubleshooting doc disagree. This repo already passes `secrets.GH_TOKEN` from `pull_request_target`; that is the path the troubleshooting doc endorses, and it is the one the auto-merge workflow uses today.

## Which encoding approach is most robust for the bump map?

### Takeaway
Parse Dependabot’s `update-type` trailer in a semantic-release analyze step for the automatic map (patch/minor → package patch, major → package minor). Use retitle plus `gh pr merge --merge --subject`, and a repo default of “PR title / blank body,” only for the human override to package major. Do not rewrite commits on `dependabot/*`, do not change the global prefix to `fix`, and do not put the Dependabot PR body in the merge commit.

### Cited Findings
- Automatic map inputs that already exist in git history: per-dependency `update-type` in the commit YAML, and `Updates \`name\` from A to B` lines. — [dependabot-core #8217](https://github.com/dependabot/dependabot-core/issues/8217); [fetch-metadata PR 632](https://github.com/dependabot/fetch-metadata/pull/632); [garm commit e503948](https://github.com/cloudbase/garm/commit/e503948c4012d0ef4189f84515153fd1dfd2b89f)
- Nothing in that metadata means “breaking for consumers of this package.” Dependency major is only `version-update:semver-major`. — [fetch-metadata README](https://github.com/dependabot/fetch-metadata/)
- Prefix configuration cannot express three levels. — [Dependabot options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)
- Real retitle workflows change the PR title and, where they merge, often squash. One example rewrites a missing conventional prefix, then `gh pr merge --auto --squash --subject "chore(deps): $PR_TITLE"`. Another only rewrites `chore(deps)` to `security(deps)` when a GHSA id is present. Squash is what makes the PR title the only commit on `main`. — [SeWieland workflow run](https://github.com/SeWieland/Transiever.SieveRuler/actions/runs/29721488092/workflow); [microsoft/physical-ai-toolchain](https://github.com/microsoft/physical-ai-toolchain/blob/main/.github/workflows/dependabot-security-prefix.yml)
- This repo disallows squash in the auto-merge workflow (`--merge` is explicit) and its release rules ignore `chore`. — `.github/workflows/dependabot-auto-merge.yml`; `.releaserc.js`
- Release notes are produced from parsed commits by `@semantic-release/release-notes-generator`. They are not an input that selects the bump. The repo already lists that plugin. — `.releaserc.js`; [commit-analyzer usage, notes are a separate plugin](https://github.com/semantic-release/commit-analyzer)

### Inferences
- The plan “retitle + merge subject” is the correct squash-era pattern adapted to `--merge`, and it fixes the hole in the current command, which sets `--body` and leaves the headline as `Merge pull request #N`. It is not sufficient as the only encoding.
- Concrete improvements to that plan:
  1. Add `--subject` equal to a single-line conventional header. Keep `--body` short and written by the workflow. Never pass the Dependabot PR body.
  2. Subject map: `version-update:semver-patch` and `version-update:semver-minor` → `fix(deps): <original subject without the chore prefix>`. `version-update:semver-major` → `feat(deps): …`. Label `breaking` or `substantial` → `feat(deps)!: …` and body `BREAKING CHANGE: <why this package’s API changed>`.
  3. Set the repository merge-commit default to title = pull request title and message = blank, so a manual UI merge matches the workflow. Do not select “pull request title and description.”
  4. Retitle on `pull_request_target` with `secrets.GH_TOKEN` before arming auto-merge, and again on `synchronize`, because Dependabot’s regenerate keeps the commits and can race a title that was never the source of truth. Retitle is for humans and for the UI fallback, not for the analyzer.
  5. Add one `analyzeCommits` implementation that reads `update-type` from the YAML trailer (package patch vs package minor) and still applies the existing conventional rules, then returns the higher bump. That is what makes a manual merge, a stack landing, and a forgotten `--subject` still publish the automatic map. Package major continues to require the explicit `feat!:` / `BREAKING CHANGE:` commit, which upstream changelog text inside a `chore(deps)` commit will not trigger under the current `chore → false` rule. Keep that rule.
  6. Do not push rewritten commits to `dependabot/*`. Do not set `skip-verification` just to look at a dirty branch.
  7. Prefer `updated-dependencies-json` when deciding the subject, and ignore `direct:development` items if a Jest/TypeScript group should not ship a new package version. The stated map does not require that filter; the repo’s mixed groups make it a product choice. If the filter is adopted, a group that contains any production major is still a package minor.
  8. If a merge queue is turned on later, `--subject` stops working. The trailer parser still works. Revisit stack merge before enabling a queue.
- `chore(major)` would technically match this repo’s `scope: major` rule and ship a major, but it is a worse override than `feat(deps)!:` because the scope rules are order-sensitive and `chore` is hidden in the notes.
- Changing the Dependabot prefix to `fix` would publish dependency majors as package patches and would fight the trailer plugin if both said something different. Leave the prefix as a non-releasing type so the plugin and the explicit merge subject are the only bump sources.

### Gaps
- No fixture from this repo’s Dependabot commits was parsed, so the trailer plugin should be tested on one solo PR and one grouped PR before relying on field names.
- Whether a native stack merge creates one merge commit or one per layer was not specified in the docs. The trailer approach is valid in both cases; a subject-only approach is not.
- Pipeline aggregation when two `analyzeCommits` plugins are configured was not re-read in v25. Implement the trailer logic and the conventional rules in one plugin.
